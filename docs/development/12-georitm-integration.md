## Назначение GEORITM в проекте

GEORITM — REST API подсистемы мониторинга (`/restapi/...`, все вызовы — HTTP POST, JSON): объекты, зоны, события/тревоги, координаты, планы помещений. Цель интеграции — заменить демонстрационный источник данных кабинета на реальные данные объектов клиентов.

## Три категории статуса

### 1. Уже реализовано (в коде проекта)

- UI кабинета, полностью отвязанный от источника данных: страницы и компоненты получают данные через props, URL-константы в `config/routes/cabinet.routes.ts`.
- Контракты данных (`lib/account/contracts.ts`) — нейтральные union-типы состояний (`SecurityAlarmState`, `FireAlarmState`, `ConnectionState`), в которые маппятся статусы GEORITM.
- Barrel `lib/account/index.ts` — точка подмены реализаций.
- Механизм cookie-сессии и guard маршрутов (см. [10-cabinet-authentication.md](./10-cabinet-authentication.md)).
- Файловые пути, упоминавшиеся в старых документах, актуализированы: страницы — `app/(cabinet)/cabinet/...`, API — `app/api/cabinet/...`.

### 2. Спроектировано, но НЕ реализовано

- **`GeoritmApiClient`** (`lib/georitm/api-client.ts`, предлагается): только Node.js runtime, POST + `Authorization: Basic`, тайм-ауты через AbortController, разбор ошибок `{msg, hdr}`, ретраи только на сетевые ошибки. Первый этап — только `users/login/`, `users/logout/`, `ping/`.
- **`GeoritmSource`** (`lib/account/sources/georitm-source.ts`, предлагается): адаптер за интерфейсом источника данных кабинета; маппинг объектов/зон/событий в текущие контракты; ссылка на объект — по `extId`.
- **Переключатель источника**: переменная `ACCOUNT_DATA_SOURCE=demo|georitm` — деморежим сохраняется для локальной разработки.
- **Серверное хранилище сессий**: вход → `users/login/` → запись с `basic`-токеном GEORITM на сервере; браузеру — только **opaque session ID** в HttpOnly-cookie. 401 от GEORITM → инвалидация сессии кабинета. Это закроет текущие ограничения (отзыв сессии, rate limit — туда же).
- Кэширование и интервалы опроса (этап 7), карта на тайлах внешнего провайдера (этап 8) — значения интервалов в roadmap помечены как предположения до ответов поставщика.

### 3. Требует проверки на реальном сервере GEORITM

- Сетевая достижимость API с Amvera (whitelist/VPN? — вопрос A2), боевой хост/порт.
- Единицы Timestamp (секунды vs миллисекунды — противоречие в документации; тест 10).
- Лимиты частоты запросов, пагинация `alerts/history-*`, тайм-ауты (B1–B5).
- Срок жизни `basic`-токена и механизм продления (A5/A6).
- Правило классификации зон «охрана/пожар» (B7).
- Поведение при повторном `users/login/` и при 401 (С5).
- Наличие планов помещений и координат в реальной инсталляции (тест 11).

## Изоляция данных пользователей

Доступ определяется на стороне GEORITM (дерево объектов возвращается для текущего пользователя — `objects/objects-tree-set/`); кабинет дополнительно держит правило «данные объекта — только после серверной проверки владения» (см. [11-cabinet-data-and-access.md](./11-cabinet-data-and-access.md)). Обязательный тест изоляции (тест 5 / С1) — на тестовом контуре и повторно на production.

## Почему Basic-учётные данные нельзя в браузер/cookie

Текущий токен сессии — **подписанный, но не зашифрованный**: payload — `base64url` без шифрования, любой, у кого есть cookie (или скопировавший её), читает содержимое одним декодированием. Подпись защищает от *подделки*, но не от *чтения*. Поэтому:

- `basic`-токен GEORITM (и тем более логин/пароль) **никогда** не попадает в cookie, HTML или клиентский JS;
- он хранится **только в серверном хранилище сессий**; браузеру отдаётся непрозрачный ID;
- учётные данные GEORITM (сервисные `GEORITM_SERVICE_LOGIN`/`GEORITM_SERVICE_PASSWORD`) — только в переменных окружения сервера, не в репозитории (этап 1 плана).
