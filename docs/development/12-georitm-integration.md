## Назначение GEORITM в проекте

GEORITM — REST API подсистемы мониторинга (`/restapi/...`, все вызовы — HTTP POST, JSON): объекты, зоны, события/тревоги, координаты, планы помещений. Цель интеграции — заменить демонстрационный источник данных кабинета на реальные данные объектов клиентов.

## Три категории статуса

### 1. Уже реализовано (в коде проекта)

- UI кабинета, полностью отвязанный от источника данных: страницы и компоненты получают данные через props, URL-константы в `config/routes/cabinet.routes.ts`.
- Контракты данных (`lib/account/contracts.ts`) — нейтральные union-типы состояний (`SecurityAlarmState`, `FireAlarmState`, `ConnectionState`), в которые маппятся статусы GEORITM.
- Barrel `lib/account/index.ts` — точка подмены реализаций.
- Механизм cookie-сессии и guard маршрутов (см. [10-cabinet-authentication.md](./10-cabinet-authentication.md)).
- Файловые пути, упоминавшиеся в старых документах, актуализированы: страницы — `app/(cabinet)/cabinet/...`, API — `app/api/cabinet/...`.

### 2. Спроектировано, но НЕ реализовано

- **`GeoritmApiClient`** (`lib/georitm/api-client.ts`, предлагается): только Node.js runtime, POST + `Authorization: Basic`, тайм-ауты через AbortController, разбор ошибок `{msg, hdr}`, ретраи только на сетевые ошибки. Первый этап — только `users/login/`, `users/logout/`, `ping/`.
- **`GeoritmSource`** (`lib/account/sources/georitm-source.ts`, предлагается): адаптер за интерфейсом источника данных кабинета; маппинг объектов/зон/событий в текущие контракты; ссылка на объект — по `extId`.
- **Переключатель источника**: переменная `ACCOUNT_DATA_SOURCE=demo|georitm` — деморежим сохраняется для локальной разработки.
- **Серверное хранилище сессий**: вход → `users/login/` → запись с `basic`-токеном GEORITM на сервере; браузеру — только **opaque session ID** в HttpOnly-cookie. 401 от GEORITM → инвалидация сессии кабинета. Это закроет текущие ограничения (отзыв сессии, rate limit — туда же).
- Кэширование и интервалы опроса (этап 7), карта на тайлах внешнего провайдера (этап 8) — значения интервалов в roadmap помечены как предположения до ответов поставщика.

### 3. Требует проверки на реальном сервере GEORITM

- Сетевая достижимость API с Amvera (whitelist/VPN? — вопрос A2), боевой хост/порт.
- Единицы Timestamp (секунды vs миллисекунды — противоречие в документации; тест 10).
- Лимиты частоты запросов, пагинация `alerts/history-*`, тайм-ауты (B1–B5).
- Срок жизни `basic`-токена и механизм продления (A5/A6).
- Правило классификации зон «охрана/пожар» (B7).
- Поведение при повторном `users/login/` и при 401 (С5).
- Наличие планов помещений и координат в реальной инсталляции (тест 11).

## Изоляция данных пользователей

Доступ определяется на стороне GEORITM (дерево объектов возвращается для текущего пользователя — `objects/objects-tree-set/`); кабинет дополнительно держит правило «данные объекта — только после серверной проверки владения» (см. [11-cabinet-data-and-access.md](./11-cabinet-data-and-access.md)). Обязательный тест изоляции (тест 5 / С1) — на тестовом контуре и повторно на production.

## Почему Basic-учётные данные нельзя в браузер/cookie

Текущий токен сессии — **подписанный, но не зашифрованный**: payload — `base64url` без шифрования, любой, у кого есть cookie (или скопировавший её), читает содержимое одним декодированием. Подпись защищает от *подделки*, но не от *чтения*. Поэтому:

- `basic`-токен GEORITM (и тем более логин/пароль) **никогда** не попадает в cookie, HTML или клиентский JS;
- он хранится **только в серверном хранилище сессий**; браузеру отдаётся непрозрачный ID;
- учётные данные GEORITM (сервисные `GEORITM_SERVICE_LOGIN`/`GEORITM_SERVICE_PASSWORD`) — только в переменных окружения сервера, не в репозитории (этап 1 плана).

## Порядок внедрения (сводка этапов — детали в roadmap)

0. Ответы поставщика (категория A) → 1. Сетевой доступ и env-конфигурация → 2. Безопасная авторизация и серверное хранилище сессий → 3. Smoke-тесты API и клиент чтения → 4. `GeoritmSource` и подключение списка объектов → 5. Состояния и зоны → 6. История событий → 7. Кэширование/опрос → 8. Карта → 9. ## Статус реализации (обновление 2026-11-14, этап 2 интеграции)

Первый вертикальный сценарий реализован: вход через GEORITM и просмотр реальных
объектов. Ниже — подтверждённые факты и принятые решения; прежние выводы не
пересматриваются, если не отмечено иное.

### Подтверждено на реальном сервере (первый диагностический прогон, скрипт `scripts/georitm-diagnostics.mjs`)

- **Версия сервера: 2.27.0, сборка 07.11.2019** (не 2.0.3/2.1.1 из примеров документации).
- `ping/`, `version/`, `users/login/`, `objs-groups/group/`, `objects/objects-tree-set/`,
  `objects/obj/`, `objects/obj-card/`, `objects/get-status/`, `objects/state/` — работают.
- **Basic-авторизация подтверждена**: поле `basic` ответа login равно
  `base64(login:password)` без префикса; последующие вызовы с
  `Authorization: Basic <basic>` дают HTTP 200.
- **Сервер дополнительно возвращает сессионную cookie** (в REST-документации
  не описана) — сессия тоже работоспособна; для интеграции выбран Basic.
- **Расхождение:** `objs-groups/group/` возвращает объект `{objects, groups}`,
  а не массив; формат ответа без id документацией не раскрыт.
- **Расхождение (важно):** неверные учётные данные дают **HTTP 500** с сообщением
  «The user not found or wrong password», а не документированный 401. Клиент
  (`georitm-source.ts`) распознаёт эту ситуацию по сообщению; прочие 500
  пробрасываются как недоступность.
- Единицы Timestamp: `buildTs` пришёл не epoch-числом; правило эвристики
  (>1e12 — мс) пока не подтверждено для всех полей (вопрос B5 остаётся).
- Тестовый пользователь — **администратор** (`isAdmin=1`, `allowedActions` — 73 кода),
  один стационарный объект (offline, hasFault=1).

**Изоляция данных между обычными клиентами требует отдельного тестирования
с двумя GEORITM-пользователями, имеющими разные наборы объектов.** На тестовом
администраторе изоляция не подтверждена; кабинет дополнительно проверяет
принадлежность объекта списку, полученному от GEORITM, и возвращает 404
для чужих и несуществующих объектов.

### Реализовано в коде (этап 2)

| Компонент | Файл | Роль |
|---|---|---|
| Серверный клиент GEORITM | `lib/georitm/api-client.ts` | Единая точка POST/URL/Basic/тайм-аутов; классификация ошибок `GeoritmApiError` (network/timeout/http + msg); типизация подтверждённых ответов; только Node.js runtime |
| Хранилище сессий | `lib/account/session-store.ts` | Файл на постоянном томе Amvera `/data/account-sessions` (dev: `.data/`, в `.gitignore`); opaque session ID (256 бит) в HttpOnly-cookie; в файле — только SHA-256 ID; TTL 8 ч; отзыв (logout, 401 GEORITM) |
| Источник данных GEORITM | `lib/account/georitm-source.ts` | Маппинг объектов/зон в контракты кабинета; фильтрация чувствительных полей `obj-card` (`settings` исключён целиком); проверка владения по дереву GEORITM; журнал событий — `null` (методы `alerts/*` не проверены) |
| Диспетчер источника | `lib/account/source.ts` + `source-config.ts` | `ACCOUNT_DATA_SOURCE=demo\|georitm` (по умолчанию `demo`); UI источника не знает |
| Вход/выход | `app/api/cabinet/login`, `logout` | Диспетчер учётных данных; rate limit 5 попыток / 15 мин (в памяти процесса); GEORITM-недоступность → 502, неверные данные → 401; logout отзывает серверную сессию |

- Контракты переименованы в нейтральные: `DemoMonitorObject` → `MonitorObject`,
  `DemoObjectZone` → `ObjectZone`, `DemoEventType` → `MonitorEventType` (план
  этапа 4 из `INTEGRATION-ROADMAP.md`); расширения: `securityAlarm` получило
  `'partial'` (isGuarded=2), `fireAlarm` — `'unknown'` (поле «пожар» на уровне
  объекта в GEORITM отсутствует — вопрос B7), `extId` — внешний номер,
  `updatedAt` опционален (единицы времени не подтверждены — не заполняется
  при сомнении).
- Состояния объекта: `securityAlarm` — приоритет тревога > неисправность >
  isGuarded (0/1/2 → disarmed/armed/partial); `connection` — isOnline
  (отсутствие данных → `offline`, не «норма»).

### Проверено фактически (dev-сервер, curl)

- demo: guard (307), API без cookie (401), вход/выход, чужой объект (404),
  пустой список у пользователя без объектов.
- georitm: вход тестовыми данными → 200, cookie `g...` (44 симв., не декодируется
  в учётные данные), `/cabinet` показывает реальные объекты, объект 59 → 200,
  неизвестный id → 404, id-инъекция → 404, журнал событий → явная пометка
  «пока не подключён», logout → отзыв (старый cookie: страницы 307, API 401),
  demo-токен в georitm-режиме → 401, недоступный GEORITM → 502, rate limit
  (5×401 → 429).

### Пока не реализовано / не проверено

- Журнал событий (`alerts/*`) — методы на реальном сервере не вызывались;
  источник возвращает `null`, страница показывает «пока не подключён».
- `obj-scan/` — активное сканирование прибора; не вызывалось (нужны
  обоснование и согласование).
- Карта на тайлах, real-time, отчёты — прежний план без изменений.
- Срок жизни Basic/cookie GEORITM, поведение при повторном входе — вопросы
  A5/A6 поставщику. Смена пароля пользователем через кабинет не реализуется.
- Rate limit в памяти процесса — достаточен для одиночного экземпляра Amvera;
  при масштабировании заменить распределённым решением.
- **HTTPS до GEORITM**: сейчас тестовый контур доступен по `http://` — для
  production транспорт нужно обеспечить или подтвердить (VPN/закрытый контур).
- **Изоляция обычных клиентов** — см. выше, обязательный тест С1 со вторым
  пользователем.
