# 14. Диагностика проблем

Симптом → причина → где проверять → что делать. Многие пункты подтверждены фактической диагностикой в этом проекте (см. примечания).

## Браузер и гидратация

| Симптом | Возможная причина | Где проверять | Что делать |
|---|---|---|---|
| `Hydration failed because the server rendered HTML didn't match the client` | Расхождение сервер/клиент HTML; в этом проекте историческая причина — **зомби-Service Worker**, отдававший устаревший HTML/чанки | DevTools-консоль; `navigator.serviceWorker.controller` в консоли браузера | Если SW контролирует страницу, а проект SW не использует → удалить регистрацию (ниже) |
| `Encountered a script tag while rendering React component…` | Сырой `<script>` внутри React-компонента. В коде проекта этого уже нет (все скрипты через `next/script`, `app/layout.tsx`); предупреждение может приходить из **закэшированного старого HTML** зомби-SW | `grep -rn "<script" --include="*.tsx"` по `app/ components/ widgets/` — совпадений в JSX быть не должно | Если найден свой `<script>` в JSX — заменить на `<Script>` из `next/script`. Если нет — чистить SW-кэш браузера |
| Кнопки «Войти»/«Выйти» не реагируют, fetch не отправляется | React не гидратировался (частая причина — зомби-SW перехватывает чанки) | В консоли: `Object.keys(кнопка).some(k => k.startsWith('__react'))` — 0 ключей = не гидратирован | Удалить зомби-SW (ниже), перезагрузить страницу |
| Открытие сайта «само» попадает в кабинет / старый контент | Зомби-SW отдаёт кэшированные навигации | `caches.keys()` в консоли браузера — чужие кэши (в кейсе проекта: `nutriarium-static-v1`) | Разрегистрировать SW и очистить кэши (ниже) |
| Открытие страницы с «чистого» профиля — нет ошибок, всё работает | — | — | Значит проблема была в локальных данных браузера, а не в коде |

### Ручная очистка старого Service Worker (Chrome/Edge)

1. Откройте `chrome://serviceworker-internals` (или DevTools → Application → Service Workers).
2. Найдите записи для `localhost:3000` (или production-домена), чей скрипт — не из этого проекта (в кейсе проекта был `/sw.js` от старого проекта «Nutriarium»).
3. Нажмите **Unregister**.
4. DevTools → Application → Storage → **Clear site data** (или вручную удалить чужие записи в Cache Storage).
5. Перезагрузите страницу.

Автоматическая защита: в dev-сборке (`app/layout.tsx`, скрипт `dev-sw-zombie-cleanup`) проект сам разрегистрирует SW, чей скрипт возвращает не-200/недоступен, — **только** для `localhost`/`127.0.0.1` и только в dev. Она была проверена фактически: специально созданная тестовая регистрация с удалённым скриптом удалилась автоматически при следующей загрузке. Production-домены скрипт не затрагивает; CacheStorage скрипт не трогает.

## Авторизация и кабинет

| Симптом | Возможная причина | Где проверять | Что делать |
|---|---|---|---|
| Неожиданный редирект на `/cabinet/login` | Нет/просрочена/невалидная cookie `ka_account_session`; это штатное поведение guard-а (`app/(cabinet)/cabinet/layout.tsx`) | DevTools → Application → Cookies | Войти заново; в dev — учётные записи видны на форме входа |
| Кабинет открывается без входа | В браузере осталась валидная cookie сессии (в dev секрет фиксированный — старые токены долго живут) | DevTools → Cookies; сервер: `GET /api/cabinet/session` | Это не уязвимость; для проверки «анонимного» сценария удалить cookie |
| Вход не работает, `POST /api/cabinet/login` → 503 | Production-сборка: демо-вход отключён **намеренно** (`isDemoLoginEnabled()`) | `NODE_ENV` запущенного сервера | Это штатное поведение. Для проверки демо-входа запускать `npm run dev` |
| Вход не работает, `POST` → 401 | Неверный логин/пароль | Тело ответа: «Неверный логин или пароль» | В dev проверить логин/пароль на странице входа |
| Вход не работает даже с верными данными, в логах «Секрет сессии недоступен» | Не задан `ACCOUNT_SESSION_SECRET` (prod) | Переменные окружения | Задать секрет (см. [13-deployment-and-environment.md](./13-deployment-and-environment.md)) |
| API кабинета отвечает 401 | Нет/невалидная сессия | DevTools → Network → заголовки запроса (cookie уходит?) | Проверить, что cookie отправляется; перевойти |
| Объект открывается как 404, хотя «он есть» | Чужой или несуществующий id — **специально неотличимые** 404 (`findDemoObjectForUser`) | Список своих объектов на `/cabinet`; `lib/account/demo-data.ts` | Открывать объекты только из своего списка. Это защита, а не баг |
| Выход «не работает» | Зомби-SW съел fetch (исторический кейс) или cookie не удалилась | Network: уходит ли `POST /api/cabinet/logout`; `console` | Чистить SW; проверить, что после logout cookie пустая/удалена |

## Сборка и типы

| Симптом | Возможная причина | Где проверять | Что делать |
|---|---|---|---|
| `npm run build` падает | Ошибка типов/импорта; чаще — ссылки на несуществующие модули после перемещений | Вывод сборки (первые ошибки) | Исправить по выводу; `npx tsc --noEmit` для полной картины |
| `tsc --noEmit` ругается на `.next/types/...` | Устаревшие сгенерированные валидаторы маршрутов (после перемещения страниц) | Пути ошибок — внутри `.next/` | Перезапустить dev или `npm run build` — валидаторы перегенерируются; ошибки **только** в `.next` — не ошибки кода |
| В сборке не появился маршрут | Файл `page.tsx`/`route.ts` не в том каталоге (Route Group ≠ URL) | Список маршрутов в конце лога сборки | Сверить структуру каталогов с [06-routing-and-pages.md](./06-routing-and-pages.md) |

## Локальный запуск

| Симптом | Возможная причина | Где проверять | Что делать |
|---|---|---|---|
| «Port 3000 is in use…» | Остался процесс старого dev-сервера | `netstat -ano \| findstr :3000` | `taskkill /PID <pid> /F` (Windows) |
| «Another next dev server is already running» | Второй dev-сервер на том же каталоге | Список процессов node | Оставить один экземпляр |
| Первая загрузка страницы 30–60 с | Компиляция по требованию (+медленная ФС) | Лог dev-сервера («Slow filesystem detected») | Норма; подождать |
| Правка env-переменной не применилась | `NEXT_PUBLIC_*` инлайнятся при компиляции | — | Перезапустить dev-сервер |
| Странное поведение после множества правок | Кэш Turbopack | `.next/dev/` | Остановить сервер, удалить `.next/`, запустить снова |

## Исторический кейс (зафиксирован при диагностике этого проекта)

Полный набор симптомов «вход не работает + кнопки мертвы + открытие сайта уводит в кабинет + `GET /sw.js 404`» имел **одну первопричину**: активный Service Worker от ранее запускавшегося на `localhost:3000` проекта (кэш `nutriarium-static-v1`, скрипт `/sw.js`). SW перехватывал запросы страницы → React не гидратировался → обработчики кнопок не подключались; устаревший кэш воспроизводил ошибки, которых в коде уже не было. Серверный код авторизации при этом работал корректно (подтверждено HTTP-тестами). Решение — разрегистрация SW; профилактика — dev-скрипт автоочистки (`app/layout.tsx`).
