# E10 — Постраничный журнал событий и инкрементальная история GEORITM

**Проект:** kvadro-2026-next, личный кабинет клиента «Квадро-Арсенал»
**Дата:** 2026-11-15
**Статус:** реализация завершена. Все вызовы GEORITM — read-only (`alerts/history-on-obj/`, `alerts/history-by-obj/`, справочники); управляющие методы не вызывались.

## 1. Фактический контракт `alerts/history-on-obj/` (2.27.0, подтверждено пробой)

Параметры: `objectId: int`, `from: Timestamp|null`, `to: Timestamp|null`; ответ — плоский массив `ObjectAlert`/`ObjectAlertLog` (как у `history-by-obj/`).

- **Единицы `from/to` — миллисекунды** (окно в секундах даёт пустой ответ).
- **Фильтрация и сортировка — по `receivedAt`** (времени получения станцией), а не по `alertTs`: записи с `alertTs` из 2003 г. и `receivedAt` в 2026 г. возвращаются окном 2026 года.
- **Границы включающие** на миллисекундной точности. У действий (`ObjectAlertLog`) хранимая метка **суб-секундная**: окно `[receivedAt, receivedAt]` действие не находит, `[receivedAt−1, receivedAt+1]` — находит.
- **Одинаковые `receivedAt` существуют** (3 пары на тестовом объекте), обе записи возвращаются одним окном.
- **`limit`/`offset`/`cursor`/`total` в API нет** — это date-based pagination: окно возвращает все записи интервала.
- `from=null` → «со времени последнего сброса» (тревоги), `to=null` → «по текущее время»; `from=-1` ведёт себя как «со времени последнего сброса» (включая саму запись сброса). Кабинет всегда передаёт обе границы явно.
- Ошибки: чужой/несуществующий `objectId` → HTTP 401 «Invalid username or wrong password»; строковый `from` → HTTP 500 с сообщением о приведении типов; пустое окно → 200 `[]`.

## 2. Отличия от `history-by-obj/`

`history-by-obj/` — последние ≤1000 событий + ≤1000 действий одним вызовом, без параметров периода. `history-on-obj/` — произвольный период, без ограничения по количеству, но без постраничных механизмов. Ни один из методов не отдаёт total.

## 3. Механизм постраничной загрузки (реализация)

GEORITM не предоставляет настоящих курсоров — построен честный механизм **якорных временных границ** (не выдаваемый за cursor-based API):

- **Страница 1 / обновление** — «голова»: один вызов `history-by-obj/` (новейшие ≤1000+1000), при нехватке после фильтрации — продолжение окнами `history-on-obj/` глубже покрытия головы.
- **Страницы 2+** — «шагающие» окна от якоря: лесенка 1ч → 6ч → 24ч → 7д → 31д → 92д → 366д, до набора `pageSize+1` записей (проба «есть ещё»). Если лесенка исчерпана, **конец истории доказывается финальной пробой до начала эпохи** — одно дополнительное окно; поэтому «следующая страница» отключается только тогда, когда глубже записей действительно нет.
- **Якорь** = граница `{t, skip[]}`: метка `receivedAt` последней записи предыдущей страницы и id записей с этой меткой, уже показанных на ней (разрез страницы может пройти посередине группы одинаковых меток). Якорь подписывается HMAC-SHA256 (`v1.<payload>.<hmac>`, секрет сессии) и связывается с объектом, фильтром и направлением; подделка/чужой якорь → молчаливый возврат на первую страницу.
- **Навигация** («предыдущая»/«следующая») строится из одного якоря: выборка «вглубь» и «наверх» от одной границы; повторный показ страницы воспроизводит ровно тот же набор записей.

## 4. Фильтрация

GEORITM фильтр по типу не предоставляет — фильтр применяется на сервере кабинета после классификации (mapper и группы не изменялись). Фильтрация работает по всей достижимой глубине: страница фильтра добирается окнами до заполнения или доказанного конца. Изменение фильтра/размера страницы сбрасывает позицию (якорь действителен только в своём фильтре — проверяется подписью).

## 5. URL и Back/Forward

`?type=` (фильтр), `?size=` (15/25/50/100), `?page=` (номер для отображения), `?c=` (подписанный якорь). Страница 1 — канонический URL без `c`; позиции без якоря канонизируются на страницу 1. Back/Forward и обновление страницы восстанавливают позицию по якорю (проверено в браузере).

## 6. Дубли и пропуски

- Окна перекрываются намеренно (суб-секундная точность действий не даёт неперекрывающихся границ); повторы убирает дедупликация по `alertId`/`id` (префиксы `alert:`/`action:`).
- skip-список обрабатывает одинаковые `receivedAt` на разрезе страниц.
- Проверено: смоук (20 сценариев, включая разрез группы одинаковых меток и новые записи между запросами) и live-прогон фактического кода на реальном сервере — 5 страниц × 7 записей = 31 запись, 0 дублей, 0 потерь.

## 7. Безопасность и нагрузка

- Владение объектом проверяется до любого вызова `alerts/*` (чужой объект неотличим от несуществующего); 401 отзывает сессию.
- Размер страницы — белый список 15/25/50/100; якорь валидируется (подпись, границы, skip-шаблон); тайм-ауты и классификация ошибок — существующие в api-client.
- Число запросов на страницу: 1 (голова) либо 1–8 окон; бесконечные циклы исключены (лесенка конечна, проба одна).
- Кэши: справочник шаблонов (TTL 10 мин, по пользователю — без изменений), типы журнала для чипов фильтров (в памяти процесса, `пользователь:объект`, TTL 10 мин, при холодном кэше — чипы по текущей странице). Порции истории не кэшируются: свежесть важнее, а порции дёшевы.

## 8. Ограничения

- total у GEORITM нет: количество страниц и «переход в конец» не показываются (в демо-режиме total известен и показывается).
- Фильтр по типу — кабинетный: редкий тип глубже ~1,5 лет истории добирается финальной пробой, которая у объекта с долгой тишиной возвращает сразу всю старую часть журнала (один запрос на страницу, только у «хвоста»).
- Порядок страниц — по `receivedAt` (как фильтрует GEORITM); внутри страницы записи сортируются по `occurredAt`. Импортированные записи (`alertTs` сильно старше `receivedAt`) отображаются в позиции получения.
- Кэш типов чипов и якоря живут в памяти процесса: переживать рестарт не обязаны (якорь после рестарта → тихий возврат на страницу 1).
- Изоляция данных между обычными (не-администраторскими) GEORITM-пользователями по-прежнему требует отдельной проверки (см. E8, риск 1).
