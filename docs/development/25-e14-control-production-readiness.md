## 3. Аудит canArm

### 3.1. Контракт по документации [Док]

- `canArm` — Boolean, «Возможность управления постановки и снятия
  разделов стационарного объекта», условие наличия — «Если есть данные».
  Документирован **ровно в двух методах**: `objects/obj/` и
  `objects/obj-details/` (в исходном docx это строки таблиц полей;
  формулировка идентична в обоих). В `objects/objects-tree-set/`
  не документирован [Док-отсутствие].
- В примере ответа `objects/obj/` документ сам показывает **условное
  присутствие**: мобильный объект (id 39, `objType:"0"`) — без `canArm`;
  стационарный (id 40, `objType:"1"`) — `"canArm": true`. Примеров с
  `canArm: false` в документе нет ни одного.
- Других упоминаний «возможности управления» объектом в документе нет:
  поиск по тексту даёт только две таблицы полей (obj/, obj-details/).

## 4. Аудит restricted

1. **Уровень ограничения.** Формулировка «Ограничение доступа … Если
   установлен код ограниченной роли пользователя» [Док, идентична в
   tree-set/obj/obj-details] связывает поле с **ролью пользователя** на
   уровне записи объекта → измерение «пользователь × объект». Привязка
   к операции (arm vs disarm) документацией не раскрывается
   **[Не установлено]**.
2. **Как определяется ограниченная роль** — в API нет метода каталога
   ролей или признака «ограниченная роль» [Док-отсутствие];
   `users/login/` возвращает `roles[] {code, name, id}` [Док], но какой
   код роли является «ограниченным» — **[Не установлено]**.
3. **Связь с `allowedActions`** — не описана [Док-отсутствие].
4. **Взаимодействие с `objects/arm/`/`disarm/`** — не описано
   [Док-отсутствие]; проверка требует write-вызова (запрещены).
5. **Семантика отсутствия поля** — документированное условие «Если
   установлен код ограниченной роли пользователя» описывает, *когда*
   поле присутствует; явной оговорки о семантике отсутствия нет.
   Вывод «отсутствие ⇒ ограничение не установлено» согласуется с
   условием и фактом (у администратора контура поле всегда отсутствует),
   но прямо документацией не сформулирован — интерпретация E12.2
   **сохранена без изменений**.
6. **Присутствие только в определённых сценариях** — да, по условию
   «если установлен код…» [Док].
7. **Отдельный метод эффективных прав** — отсутствует [Док-отсутствие];
   `users/children/` возвращает только список дочерних пользователей
   `{id, username, fullname}` [Док].

**Итог:** семантика `restricted` не менялась (изменение запрещено
постановкой без доказанного контракта). Для допуска требуется ответ

[API].

## 5. Аудит allowedActions и модель авторизации

**Сигналы, доступные API** (все сверены с docx) [Док]:

| Сигнал | Источник | Измерение |
|---|---|---|
| Сессия кабинета + GEORITM Basic | session-store / `users/login/` | глобально |
| `allowedActions: String[]` «Коды разрешенных операций» | `users/login/` | пользователь × тип операции (глобально) |
| `isAdmin`, `roles[]` | `users/login/` | пользователь |
| `restricted` Integer | tree-set/obj/obj-details | пользователь × объект |
| `canArm` Boolean | obj/, obj-details/ | объект |
| `objType` | tree-set/obj/ | объект (техническая поддержка) |
| `obj-areas/` → `num` | объект × раздел | адресуемость |
| `objects/state/` → 1/2 | прибор × раздел | фактическое состояние |
| `isFromIDP` | obj/ | путь доставки данных/команд |

**Формальная модель кабинета** (реализована в
`computeControlAvailability`, `georitm-control.ts:134`) — пять
независимых условий, объединяемых только для вердикта «available», без
сведения в один Boolean:

1. право пользователя (`allowedActions` → проекция сессии
   `SessionControlPermissions`, `georitm-source.ts:181`) — глобальное
   право на тип операции;
2. `canArm === true` — техническая возможность объекта;
3. `restricted !== 1` — отсутствие ограничения «пользователь × объект»;
4. IMEI разрешён серверно — адресуемость прибора;
5. состояние раздела известно (`objects/state/` 1/2) — фактическая
   доступность раздела; плюс кабинетная политика
   already-in-state поверх фактического состояния.

Независимость сохранена кодом: явные запреты (`false` право,
`canArm === false`, `restricted === 1`) дают `'no-permission'`;
недостаток данных — `'unknown'`; объекты `objType === '0'` —
`'unsupported'`. Коды `objects.arm`/`objects.disarm` подтверждены
фактическим каталогом 73 кодов [API, E8]. Связь наличия кода с
серверной проверкой write-метода — **[Не установлено]** (кабинет
консервативно считает код необходимым, но не достаточным).
`users/children/` к правам отношения не имеет [Док].

## 6. Аудит IDP

1. **`isFromIDP`** [Док]: «Работа с объектом через IDP» — приёмная
   подсистема транслирует протоколы приборов. Тестовый объект:
   `isFromIDP=true` [API].
2. **Путь доставки команд для IDP-объектов основным API** — ни основной,
   ни IDP документ не описывает [Док-отсутствие]; **[Не установлено]**.
3. **Условия управления IDP-объектами** — не описаны; в IDP есть
   механизмы запрета постановки `objects/lock/`, `lock-state/`,
   `block/unblock/` [Док], не проброшенные в основной API.
4. **Ограничения по типам оборудования** — не описаны [Док-отсутствие].
5. **Может ли основной REST API отправлять команды IDP-объектам** —
   совпадение схемы `{imei, area}` → `{success}` между документами не
   доказывает совпадения поведения; **[Не установлено]** (проверка —
   write-вызов, запрещён).
6. **Как определить поддержку операции** — документированного признака,
   кроме условного `canArm`, нет.
7. **Распознавание отказа устройства** [Док, IDP]: явный отказ
   `{"msg": "Command was declined by the device", "hdr": "Failed to
   submit the command", "data": null}` при приборе вне связи. Для
   основного API форма отказа не описана [Док-отсутствие]; кабинет
   классифицирует явный HTTP-отказ как `rejected`, сеть/тайм-аут —
   `unknown`, что безопасно при любой форме [Код].

**Политика (предложение, раздел 6 постановки):** до ответа поставщика
(P2) IDP-объекты должны оставаться недоступными. **Сейчас это
выполняется де-факто** [Код+API]: единственный носитель положительного
признака `canArm` сервером не заполняется → capability `unknown` →
запрет. Явный кодовый guard «`isFromIDP=true` → запрет» **намеренно не
реализован**: он кодировал бы гипотезу о том, что основной API не
исполняет команды IDP-объектов, а это не доказано; при ответе
поставщика «основной API транслирует команды в IDP» такой guard
потребовался бы удалять. Резолвер не ослаблялся. Тест E12.21
подтверждает: `isFromIDP: true` без `canArm` не разрешает управление
[Тест].

## 7. Аудит подтверждения доставки и выполнения

По документации [Док]:
1. `{success: 1}` в arm/disarm основного API — «Результат исполнения
   1-выполнено»; метод-специфичных ошибок не описано. Общие ошибки API:
   401 (авторизация), 400 (параметры), 500 (прочие), тело
   `{msg, hdr, data}` [Док]. Что именно означает «выполнено»
   (принято/передано/исполнено прибором) — не установлено (P3).
2. IDP документирует единственный явный отказ команды — «Command was
   declined by the device» (см. раздел 6.7).
3. Справочника кодов событий группы 4 в поставляемой документации нет:
   `Georitm_REST_API_Описание_формата_отчетов.docx` описывает форматы
   отчётов и кодов 402/450 не содержит (проверено поиском). Коды
   4501/4503/9201 (отказы) и 402.x (фактические взятия/снятия) — из
   проб и классификатора кабинета E11 [API, Код].
4. `objects/state/` — карта `{num: 1|2}` [Док].

По коду [Код] (`control-engine.ts`, `georitm-control.ts`):
5. Изменение `objects/state/` в целевое значение — единственное
   положительное подтверждение (`confirmed`); `{success: 1}` исходом
   не считается; окно 75 с, опрос 3 с.
6. Задержка команды → состояние: наблюдавшаяся 2–3 с [API, E11]; окно
   75 с покидает запас.
7. **Корреляция «чужой/более ранней операции»:** подтверждение по
   состоянию причинно-нечувствительно — переход в целевое состояние,
   вызванный *другой* операцией в окне наблюдения (другая сессия
   кабинета, пульт, панель), засчитается как подтверждение текущей
   команды. Отказ-коды журнала коррелируются строго по `area` и
   соответствию действия (4501↔disarm, 4503/9201↔arm), журнал
   запрашивается от старта команды −1 с. Риск ложного положительного
   подтверждения ограничен:guard `in-flight` действует на пару
   «сессия × объект × раздел» — **одновременная команда другого
   пользователя/канала на тот же раздел не блокируется** [Код,
   ограничение]. Усиление без write-проб возможно и предложено ниже
   (7.1).
8. Одновременное изменение другим пользователем — см. п.7; результат
   при расхождении остаётся честным (confirmed по факту состояния).
9. Отсутствие события/перехода за окно → `unknown` → cooldown 120 с,
   повтор заблокирован сервером (409) и UI [Код, Тест E12.16].
10. Автоматический повтор исключён: `send()` вызывается ровно один раз
    [Код, Тест E12.8 «отправка ровно одна»].

### 7.1. Предложение усиления корреляции (не реализовано)

Требует подтверждения поставщиком — значит, в рамках E14 не
реализуется («Не меняй рабочую логику подтверждения без доказанного
основания»). Вариант: засчитывать `confirmed` только при
(а) переходе `objects/state/` в целевое состояние **и**
(б) событии группы 4 факта взятия/снятия (класс 402.x) по разделу
команды с временной меткой ≥ старта команды. Это устранило бы
ложное подтверждение чужой операцией. Блокер: точный справочник кодов
402.x и гарантия их доставки в `alerts/history-on-obj/` не
документированы (вопрос поставщику P7 — расширен в разделе 12).

## 8. Аудит ownership и feature gate; реализованное исправление

**Наблюдение E13 подтверждено кодом:** при выключенном gate маршрут
команды выполнял `findObjectForUser` (read-вызовы `objects-tree-set/`
и `objects/obj/` через `fetchOwnedObjects`/`fetchOwnedObject`,
`georitm-source.ts:526`) **до** gate-проверки в `executeObjectControl`
[Код: прежний порядок route.ts].

**Анализ безопасности переноса gate раньше ownership:**

- утечка существования чужих объектов — невозможна: ответ 403
  `gate-disabled` одинаков для несуществующего, чужого и своего объекта;
- одинаковое внешнее поведение несуществующего и чужого — сохраняется
  (оба получают 403; изменение относительно прежнего: они получали 404
  — изменение зафиксировано ниже);
- отзыв сессии при 401 GEORITM — не нарушается: `getSessionUser` читает
  локальный session-store без вызовов GEORITM; при выключенном gate
  маршрут теперь не делает вызовов GEORITM вовсе, поэтому GEORITM-401 на
  этом маршруте недостижим; отзыв сессии при утрате GEORITM-credentials
  сохранён на всех остальных путях (рендер страниц, partitions,
  события) и на данном маршруте при включённом gate;
- новые GEORITM-запросы при выключенном gate — не добавлены; наоборот,
  устранены существовавшие read-вызовы.

**Реализовано (минимально):** в `route.ts` gate-проверка перенесена на
позицию после авторизации (401) и валидации тела (400), но до
`findObjectForUser`; ранний ответ `403 {success:false, error:
'Управление охраной отключено', controlDisabled: true}`. Проверка
`executeObjectControl`/`executeGeoritmControlCommand` сохранена —
defense in depth не ослаблялся (gate теперь проверяется трижды).
Разрешение постановки: раздел 9 («Если безопасное изменение возможно,
реализуй его минимально и добавь тесты»).

**Тесты:** `scripts/control-ui-smoke.mjs` дополнен пятью статическими
проверками порядка (gate присутствует; gate до `findObjectForUser`;
ранний ответ содержит `controlDisabled`; авторизация и валидация тела
остаются до gate) — 39/39 PASS [Тест]. Функциональные гарантии
«ноль вызовов при выключенном gate» остаются покрыты E12.14 (модуль)
и E12.23 (demo) [Тест].

**Семантическое изменение внешнего поведения** (зафиксировано): при
выключенном gate валидный авторизованный запрос к маршруту теперь
возвращает 403 `gate-disabled` для любого `id` (ранее: 404 для
чужого/несуществующего, 403 для своего). UI при выключенном gate
маршрут не вызывает (Safe Preview без fetch [Тест]), поэтому
пользовательское поведение не меняется.
