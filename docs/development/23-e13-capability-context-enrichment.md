## 2. Архитектура исходной цепочки данных (до E13)

Путь capability [Код]:

```
GEORITM REST API → callGeoritm (POST, JSON.parse без преобразований)
→ georitmTreeSet (objects/objects-tree-set/)
→ flattenGeoritmTree (объекты передаются как есть)
→ fetchOwnedObjects (georitm-source.ts, cache() на рендер)
→ resolveGeoritmControlContext → ctx.target («сырая» запись tree-set)
→ georitm-control: fetchControlSnapshot (obj-areas/, state/ по IMEI)
→ computeControlAvailability (DTO toPartitions и решение о команде)
```

Два входа capability: `getGeoritmControlState` (read-опрос для UI) и
`executeGeoritmControlCommand` (команда); оба вызывают
`fetchControlSnapshot`/`toPartitions`, которые берут `canArm`,
`restricted` и IMEI из `ctx.target`.

Проблема [Док + API + Код, E12.3]: `objects/objects-tree-set/` не
документирует `canArm` [Док-отсутствие] и фактически возвращает только 6
полей (`addressShort, extId, id, name, objType, objectState`) — без
`canArm`, `imei`, `restricted`, `isFromIDP` [API]. Следовательно, в
прод-цепочке `canArm` структурно недостижим (`'unknown'`), IMEI не
разрешим → `objects/state/` не вызывается → состояние `'unknown'`:
реальный объект всегда блокировался консервативно, независимо от прав.
Существующие смоуки не выявляли дефект, потому что `makeContext` задавал
`target` с imei и canArm вручную [Код].

Документированные носители `canArm` — `objects/obj/` и
`objects/obj-details/` [Док]; фактически `objects/obj/` возвращает `imei`
(строка длины 15) и `isFromIDP` [API]. `objects/obj/` уже используется в
кабинете: `fetchOwnedObject` (georitm-source.ts) — путь страницы объекта,
и `georitmObjects` — готовая обёртка api-client с подтверждённым
payload `{objectId: [id]}` (массивом; скаляр даёт HTTP 500 — дефект E11)
[Код].

## 3. Выбранный источник canArm и IMEI

**Источник — `objects/obj/` (read-only)**, по критериям задачи:

- `canArm` документирован именно в `objects/obj/` [Док] (и
  `obj-details/`, но `obj/` легче и уже используется);
- фактически возвращает `imei` [API];
- обёртка `georitmObjects` и контракт payload подтверждены работой в
  проде (путь страницы) [Код].

**Способ — обогащение контекста в georitm-control**, а не в источнике:

- оба входа capability (DTO-опрос и команда) проходят через
  `georitm-control.ts`, где транспорт инъектируется для смоуков —
  обогащение полностью покрывается тестами и mock **больше не маскирует**
  отсутствие imei/canArm в реальной цепочке;
- обогащение выполняется строго после gate- и guard-проверок → при
  выключенном gate `objects/obj/` не вызывается вообще;
- владение подтверждено до модуля (раздел 6), поэтому обогащающий запрос
  идёт только по уже подтверждённому id.

Повторное использование результата `fetchOwnedObject` (путь страницы)
отклонено: он дедуплицируется на рендер страницы (`cache()`), не
доступен в пути API-команды, возвращает проекцию `MonitorObject` без
capability-полей, и его перенос в capability потребовал бы
архитектурной перестройки. Отдельный read-вызов `objects/obj/` в
контроле управления — минимальное изменение: один запрос на опрос
состояния/команду, список объектов не затронут.

## 4. Почему выбранный способ безопасен

1. **Запрос только по подтверждённому id.** `enrichControlTarget`
   вызывает `transport.objects(ctx.basic, ctx.target.id)`, где
   `ctx.target` — запись из выдачи `objects-tree-set/` текущего
   пользователя (ownership проверен в `resolveGeoritmControlContext` до
   любых обращений с идентификаторами объекта). Данные браузера не
   используются.
2. **Строгое сопоставление ответа.** Из массива ответа используется
   запись с числовым равенством `record.id === ctx.target.id`; запись
   другого объекта отбрасывается **целиком** — данные чужого объекта не
   применяются ни при каком расхождении (включая случай, когда
   `objects/obj/` вернул только чужие записи). Проверено тестами E13.6
   (одна чужая запись) и E13.7 (чужая + своя: используется своя).
3. **Ошибка ≠ разрешение.** Ошибка `objects/obj/` (кроме 401) не
   выбрасывается и не выдумывает данные: цель остаётся без обогащения →
   `canArm`/`imei` дают `'unknown'` → управление запрещено. 401
   пробрасывается — сессию отзывает общий обработчик (механизм E12 не
   менялся).
4. **Отсутствие поля ≠ разрешение.** Переносятся только присутствующие в
   ответе поля (`record.imei !== undefined`, `'canArm' in record`,
   `'restricted' in record`); отсутствие поля в `obj/` не стирает
   значение цели. В реальной цепочке tree-set этих полей не содержит
   [API], поэтому fallback не создаёт разрешения. Семантика значений не
   менялась: `canArm: false` → `'no-permission'`, некорректный
   `canArm`/`imei`/`restricted` → `'unknown'` (E12.2 F1/F3 сохранены).
5. **Gate.** Обогащение в командном пути — после проверки
   `isGeoritmControlEnabled()` (первая строка команды) и после
   guard-проверок; в DTO-пути — после gate-проверки источника
   (`getObjectControlState`, source.ts:165). Тест E12.14 расширен:
   при выключенном gate — ноль вызовов транспорта, включая
   `objects/obj/` [Тест].
6. **Не ослаблено ничего из E12.** Ownership, права пользователя,
   addressability раздела, известность состояния, guard/cooldown,
   честная трёхзначность результата, запрет повтора при unknown — без
   изменений; `computeControlAvailability` не менялась вовсе.
7. **Минимальность запросов.** Список объектов (`fetchOwnedObjects`,
   tree-set) не изменён — лишних запросов при загрузке кабинета нет.
   `objects/obj/` добавлен только в пути управления (опрос состояния
   объекта, подготовка и сопровождение команды) — по одному вызову на
   опрос/команду.

## 6. Как обеспечена проверка ownership

Без изменений относительно E12 — ownership является обязательным
предусловием обогащения:

1. Маршрут `app/api/cabinet/objects/[id]/control/route.ts` проверяет
   сессию и вызывает `findObjectForUser` (чужой и несуществующий объект
   неотличимы — 404) до `executeObjectControl` [Код].
2. `executeObjectControl` (source.ts) проверяет gate, затем
   `resolveGeoritmControlContext`: объект должен присутствовать в выдаче
   `objects-tree-set/` текущего пользователя, иначе null → 404
   `not-owned` [Код].
3. Обогащение выполняется **после** п.2 и только по `ctx.target.id` —
   идентификатору из подтверждённой выдачи; ответ `objects/obj/`
   сверяется по строгому равенству id [Код, Тест E13.6/E13.7].
4. Ownership в demo-источнике проверен тестами E12.24 (не изменялись):
   чужой объект → null / `not-owned` [Тест].

## 11. Оставшиеся вопросы к поставщику

Без изменений относительно E12.3 (раздел 8 отчёта 22), актуальный свод —
там же (P1–P8). Ключевые для допуска управления:

- **P1 (блокер).** Заполнение `canArm` в `objects/obj/`/`obj-details/`:
  на тестовом контуре поле отсутствует у фактически управляемого объекта.
  E13 устранил **структурный** дефект источника (кабинет теперь читает
  документированный носитель), но если сервер не заполняет поле, реальный
  объект останется `'unknown'` — консервативный запрет сохранится.
  Дополнительно: является ли отсутствие поля признаком «данных нет» или
  «управление запрещено».
- **P4 / P7 (`restricted`).** Семантика по-прежнему не доказана:
  документация описывает Integer 1/0 с условием «если установлен код
  ограниченной роли пользователя», но не оговаривает семантику
  отсутствия поля; взаимодействие с `objects/arm/` (какой код
  `allowedActions` проверяется, блокирует ли ограничение arm/disarm/обе)
  не установлено. Трактовка E12.2 (отсутствие → «ограничение не
  установлено»; `1` → запрет; прочее → unknown) **сохранена без
  изменений** и требует подтверждения поставщиком.
- **P2, P3, P5, P6, P8** — поведение IDP-объектов, смысл `{success: 1}`,
  offline-прибор, `area=0`, серверный аудит.

## 12. Известные ограничения и рекомендации для следующего этапа

1. **Gate остаётся выключенным.** Обогащение устранило структурный
   блокер доступности (данные now приходят из документированного
   источника), но фактическое заполнение `canArm` сервером на тестовом
   контуре не подтверждено (P1) — включение gate преждевременно.
2. **DTO-путь при gate off.** Маршрут команды при выключенном gate
   (существующее поведение E12, не менялось) выполняет ownership-проверку
   `findObjectForUser` **до** gate-проверки в `executeObjectControl` —
   это read-вызовы GEORITM (tree-set/obj/), не связанные с capability и
   существовавшие до E13. Модуль управления при этом не выполняет ни
   одного вызова [Тест E12.14]. Если требуется «ноль вызовов при gate
   off» на уровне маршрута, нужна отдельная задача (изменит семантику
   404/403 для чужих объектов).
