## Анализ

1. **Управление работает для этой учётной записи.** Полный цикл arm→disarm исполнен
   прибором; латентность подтверждения ~4 с в обоих случаях (первый опрос каждые 5 с,
   фактическая латентность ≤ измеренной).

2. **Поля и права.** У объекта присутствовали `canArm=true` (в `objects/obj/`),
   `isFromIDP=true`, `restricted` отсутствовал; в tree-set по-прежнему только 6 полей
   (imei/canArm отсутствуют — совпадает с пробой E12.3). Права `objects.arm` /
   `objects.disarm` присутствовали в `allowedActions` пользователя-администратора.

3. **Поведение API при команде.** Контракт подтверждён: POST `{imei, area}` →
   HTTP 200 `{success: 1}` за ~1 с. `success: 1` действительно означает лишь приём;
   факт исполнения подтверждается независимо: `objects/state/` (переход 1↔2) и события
   журнала группы 4: **407.3** — дистанционное взятие, **407.1** — дистанционное
   снятие (у обоих `area` и `zone` заполнены). Отказ-коды (450.x/920.x) в успешном
   прогоне не встречались.

4. **IDP.** Команды прошли для объекта с `isFromIDP=true`. Подозрение из E11, что
   IDP-объекты неуправляемы через REST, **для этой учётной записи и объекта не
   подтвердилось**. Это наблюдение о поведении API на одном объекте, а не общий
   закон — допуска, основанного на isFromIDP, по-прежнему не требуется: управление
   разрешилось комбинацией `canArm=true` + отсутствие `restricted`.

5. **Ограничения для production-интеграции.**
   - Проверка выполнена на одной учётной записи (администратор) и одном объекте —
     поведение при `canArm=false`, `restricted=1`, не-администраторе не проверялось;
     консервативные проверки resolver'а (`canArm` строго Boolean, `restricted` —
     запрет при 1) остаются обязательными и не ослабляются этим результатом.
   - `objects/obj-areas/` вернул только разделы 0–2 при 16 разделах в `objects/state/` —
     рассогласование источников; разделам, отсутствующим в `obj-areas/`, кабинет
     корректно не даёт управление (unknown-area).
   - Подтверждение исполнения в кабинете строится на переходе состояния + кодах 407.x/
     450.x/920.x (control-engine) — реальное поведение совпало с заложенной моделью,
     включая «событие тревоги не является отказом команды».
   - Реальная тревога (130.1) во время постановки показывает, что тестовый раздел
     подключён к живым шлейфам: последующие испытания требуют координации с
     пользователем/пультом.

## Безопасность

- Секреты не выводились и не сохранялись: проверено наличие переменных без значений;
  ответ `users/login/` (содержит эхо пароля и Basic) не печатался; Authorization/Basic
  не логировались; IMEI везде маскирован; ошибки API печатались только
  классифицированными (kind/status/короткий msg).
- Write-воздействие: ровно две команды (одна arm, одна disarm), каждая — после явного
  подтверждения пользователя, с полными предпусковыми проверками; автоматических
  повторов не было; `objects/obj-scan/` и прочие write-методы не вызывались;
  `GEORITM_CONTROL_ENABLED` не включался; `.env.local` не изменялся.
- Инцидент в ходе испытания: перед первым arm-прогоном предпусковая проверка скрипта
  ошибочно блокировала команду (перепутано условие «уже в целевом состоянии»); ошибка
  была поймана ДО write-вызова (команда не отправлялась), условие исправлено, после
  чего прогон выполнен штатно.
