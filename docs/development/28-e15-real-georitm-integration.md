## 2. Разделы, работающие на реальных данных

Все разделы кабинета при `ACCOUNT_DATA_SOURCE=georitm` работают на реальных
данных GEORITM [Код, проверено трассировкой]:

| Раздел | Путь данных |
|---|---|
| Список объектов | `getObjectsForUser` → `objects-tree-set/` → `toMonitorObject` |
| Карточка объекта | `findObjectForUser` → tree-set + `objects/obj/` + `objects/state/` + `objects/get-status/` |
| Состояние (страница) | зоны из `obj-card/` (whitelist-проекция без settings), неисправности `obj-faults/`, каналы `channels/`, питание `obj-details/`.power |
| Журнал событий | `history-by-obj/` (голова) + `alerts/history-on-obj/` (окна), справочник шаблонов |
| Отчёты | `reports/{ALERTSUM,ALERTS}/{pdf,excel}` |
| Управление охраной | `getObjectControlState` / `executeObjectControl` → enrichment `objects/obj/` → `obj-areas/` + `state/` → write `arm/`/`disarm/` (только при включённом gate) |

Ошибки GEORITM нигде не превращаются в пустой список/норму: исключения
пробрасываются, страницы показывают секционные сообщения об ошибке
[Код; проверено для зон/неисправностей/каналов/управления].

Единственная декоративная заглушка — страница «Карта» (схема-план без

## 3. Исключение demo fallback (этап 2)

**Найденный дефект.** До E15 `getAccountDataSource()` возвращал `'demo'`
при любом незаданном/некорректном значении `ACCOUNT_DATA_SOURCE`, в том
числе в production. Следствия:

- production с незаданной переменной не работал бы с реальным источником
  вообще (demo-вход при этом блокировался `isDemoLoginEnabled`, т.е. в
  кабинет никто не мог войти);
- при заданном `ACCOUNT_SESSION_SECRET` production-сервер с source=demo
  принимал demo HMAC-токены сессии — фактический путь утечки demo-данных
  в production через неистёкший/подделанный по известному секрету токен;
- логика источника дублировалась трижды с риском расхождения:
  `source-config.ts`, локальная копия в `source.ts`, inline-копия в
  `app/api/cabinet/login/route.ts` (последняя в production отвечала бы
  503 «демо отключён» вместо работы через GEORITM).

**Реализовано (минимально, архитектура `source.ts` сохранена):**

1. `lib/account/source-config.ts` — введена чистая функция
   `parseAccountDataSource(value, isProduction)`:
   - production (`NODE_ENV=production`) → **всегда `'georitm'`**: незаданная
     переменная, явный `'demo'`, опечатки — всё ведёт к реальному источнику;
     demo-режим в production не активируется ни при каком значении;
   - вне production: `'georitm'` при явном значении (trim/case-insensitive),
     иначе `'demo'` — прежнее поведение разработки, demo-фикстуры и смоуки
     работают в предназначенной им среде.
2. `lib/account/source.ts` — локальная копия удалена; диспетчер импортирует
   и реэкспортирует единую функцию. Все ветки диспетчера (включая
   `verifyCredentials`, `getSessionUser` через `session.ts`, control,
   events, reports) теперь решаются одной функцией — demo-ветка в
   production недостижима ни на одном пути.
3. `app/api/cabinet/login/route.ts` — inline-копия заменена на
   `getAccountDataSource()`: в production маршрут выполняет GEORITM-вход,
   а demo-вход отклоняется `isDemoLoginEnabled` (второй рубеж сохранён).

Подмена demo-значений реальными данными в GEORITM-путях отсутствовала и
не появилось: `demo-data.ts`/`demo-events.ts`/`demo-control.ts` вызываются
только из demo-веток диспетчера и demo-ветки control (обе в production
недостижимы); фикстуры не удалены.

## 4. Определение capability управления (этап 3)

Capability-логика E12.2/E13/E13.1/E14 проверена против правил E15 —
**реализация уже соответствует, код не менялся**:

- **Правило доступности** (`computeControlAvailability`,
  `georitm-control.ts:134`, строгое сравнение без приведения типов):
  - `canArm === true` — единственный положительный признак;
  - `canArm === false` — явный запрет (`'no-permission'`);
  - `canArm` отсутствует/`null`/неожиданный тип (`1`, `0`, `"true"`) —
    `'unknown'`, управление запрещено; отсутствие поля **не** интерпретируется
    как `true`;
  - `restricted === 1` — запрет; `0` или отсутствие — ограничение не
    установлено; любое другое присутствующее значение — `'unknown'`
    (безопасный отказ);
  - `allowedActions` (`objects.arm`/`objects.disarm` в проекции сессии) —
    одно из пяти независимых условий; его наличие само по себе управление
    не разрешает, отсутствие — запрещает.
- **Источник capability:** `imei`, `canArm`, `restricted` — только из
  `objects/obj/` (enrichment E13, `enrichControlTarget`): выполняется после
  проверки владения, запись сверяется строго по id, переносится только при
  реальном наличии поля; значения из `objects-tree-set/` не используются
  (в реальной выдаче их нет — fallback на `ctx.target` не даёт разрешения,
  т.к. поля там отсутствуют). Ошибка enrichment (кроме 401) оставляет
  capability неизвестной → управление запрещено; 401 отзывает сессию.
- **Проверка использования enrichment на всех четырёх точках** [Код]:
  1) формирование DTO — `getGeoritmControlState` обогащает контекст перед
     вычислением доступности разделов (смоук E13.9);
  2) отображение кнопок — UI показывает кнопки только у разделов с
     `arm`/`disarm === 'available'` (верdict вычислен сервером);
  3) обработка команды — `executeGeoritmControlCommand` обогащает контекст
     заново и повторно вычисляет доступность перед write (defense in depth);
  4) повторная проверка на сервере — маршрутом и источником: gate трижды,
     владение, раздел через `objects/obj-areas/`, состояние через
     `objects/state/`, IMEI резолвится только на сервере.

## 5. Поведение UI

- **Без подтверждённой возможности** (нет `canArm=true`, есть `restricted=1`,
  ошибка enrichment, неизвестное состояние) — элементы постановки/снятия не
  показываются: секция объясняет причину недоступности дифференцированно
  (нет права / не поддерживается / данных недостаточно), фиктивные кнопки
  не создаются.
- **С `canArm=true` без ограничений** — управление отображается по
  фактическому состоянию раздела (`objects/state/`: под охраной → «Снять»,
  снят → «Поставить»); сохранены: диалог подтверждения, блокировка повторного
  нажатия (UI + сервер 409), состояния выполнения, подтверждение результата
  только фактическим переходом `objects/state/` (не `{success:1}`),
  обработка `confirmed`/`rejected`/`unknown` (после unknown — опрос
  partitions, cooldown 120 с на сервере).
- При выключенном feature gate сохранён Safe Preview E13.1 (без команд).

Добавлены статические проверки инвариантов в `control-ui-smoke.mjs`
(фильтр `availablePartitions`, кнопки только при `'available'`).

## 6. Серверные проверки команды

Порядок в POST `/api/cabinet/objects/[id]/control` (проверен, не ослаблен):
авторизация сессии (401) → валидация `{action, areaNum}` (400) →
**gate** (403, до ownership-чтений, E14) → владение объекта
`findObjectForUser` (404, чужой неотличим от несуществующего) →
`executeObjectControl` (gate повторно) → `resolveGeoritmControlContext`
(владение заново по выдаче tree-set) → `executeGeoritmControlCommand`
(gate в третий раз, guard повторов) → enrichment `objects/obj/` →
`objects/obj-areas/` (адрес раздела — только серверный) → `objects/state/`
по IMEI, полученному сервером из `objects/obj/` → повторное вычисление
доступности → ровно один write-вызов → наблюдение результата.
IMEI и адрес раздела от клиента не принимаются (браузер передаёт только
`{action, areaNum}`).

## 10. Остаточные риски

1. **Production-проверка выполнялась на уровне конфигурации, не живого
   сервера**: гарантия «production без demo» опирается на единственную
   функцию `source-config` и покрывается смоуком; фактический деплой не
   выполнялся (запрещён) — при выкатке проверить отсутствие
   `ACCOUNT_DATA_SOURCE=demo` в окружении production (сейчас это значение
   игнорируется, но чистота конфигурации предпочтительна).
2. **`canArm` в tree-set**: если поставщик когда-либо добавит поле в
   `objects-tree-set/`, fallback enrichment (`ctx.target.imei` и др.)
   начнёт его учитывать. Сейчас это безопасно (полей нет), но при изменении
   контракта источником нужно перепроверить правило «capability только из
   objects/obj/».
3. **Управление остаётся выключенным** (gate off):capability-путь в
   production не проверен живой командой — контрольная серия команд
   требует явного разрешения пользователя (переносится из E14.1).
4. **Ограничение смоука ownership** (GEORITM-путь владения объекта не
   покрывается скриптами из-за next/cache/сессий) — зафиксировано в E13,
   сохраняется.
5. **`source:smoke` импортирует source-config чистым Node** — если модуль
   обретёт зависимости с расширениями-less импортами, сценарий потребует
   адаптации (сейчас модуль без зависимостей — это его контракт).
