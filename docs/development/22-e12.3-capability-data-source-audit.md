## 2. Полный путь данных `canArm`

Цепочка кода [Код]: `GEORITM REST API` → `callGeoritm` (POST, JSON.parse —
без преобразований, `api-client.ts:88`) → `georitmTreeSet` →
`flattenGeoritmTree` (проход по группам, объекты передаются как есть,
без изменения полей — `api-client.ts:737`) → `fetchOwnedObjects`
(`georitm-source.ts:328`, дедупликация, без обогащения) →

при преобразовании — оно либо есть в ответе сервера, либо его нет везде.

### 2.3. Выводы по источнику canArm

1. **Кабинет берёт `ctx.target` из `objects-tree-set/` [Код], а canArm в
   tree-set не документирован [Док-отсутствие] и фактически не
   возвращается [API].** Даже если сервер заполняет `canArm` в `obj/`,
   текущая цепочка capability его никогда не увидит — источник данных
   resolver'а не содержит документированного носителя признака. Это
   структурная причина, по которой capability для реальных объектов
   останется `'unknown'`, пока `ctx.target` не обогащается из `obj/`.
2. **Попутно обнаружен более широкий дефект источника [API+Код]:** в
   фактическом ответе tree-set отсутствует и **`imei`** (6 ключей, imei
   нет), и `isFromIDP`. При этом resolver разрешает IMEI только из
   `ctx.target.imei` (`resolveImei`, `georitm-control.ts`) — то есть в
   текущей прод-цепочке **команда невозможна вдвойне**: и `canArm`, и
   `imei` дают `'unknown'` ещё до опроса `objects/state/`. Обогащённый
   объект (`fetchOwnedObject`, путь страницы объекта) делает запрос
   `objects/obj/`, который содержит и `imei` (подтверждено: строка длиной
   15), и `isFromIDP=true` [API] — но этот путь в capability resolver не
   используется. Смоук-тесты E12 этого не выявляют, потому что mock-контекст
   `makeContext` задаёт `target` с imei и canArm вручную.
3. Отдельного метода «возможности управления объектом» в API нет
   [Док-отсутствие]: признак `canArm` (объект), `canControl` (выходы,
   другое измерение), `restricted` (ограничение доступа) распределены по
   полям описательных методов; `objects/obj-controls/` — это входы прибора,
   не права (E11 3.4) и на стационарном объекте возвращает `{}` [API].
4. Семантика для `isFromIDP=true`: чем определяется отсутствие `canArm`
   у IDP-объектов и возвращается ли он когда-либо — **[Не установлено]**
   (на контуре один объект, он IDP; объекта без IDP для сравнения нет).
5. Сохраняется ли canArm при преобразованиях: вопрос снимается —
   преобразований нет [Код], поле отсутствует в самом ответе сервера.

**Итог раздела: фактический источник `canArm` для capability в текущей
реализации не установлен** — документированные носители (`obj/`,
`obj-details/`) на тестовом объекте поле не возвращают, а используемый
resolver'ом tree-set его даже не документирует. Зафиксировано как
открытый вопрос поставщику (P1, раздел 8) и как предмет обогащения
контекста (рекомендация, раздел 9).

## 3. Источник и семантика restricted

**Документация [Док]** (сверено с исходным docx): `restricted` —
**Integer**, «Ограничение доступа»: `1 — ограничен`, `0 — не ограничен`,
условие наличия: «Если установлен код ограниченной роли пользователя».
Документирован в трёх методах:

- `objects/objects-tree-set/` — поле `objs[].restricted`;
- `objects/obj/` — поле объекта;
- `objects/obj-details/` — поле объекта.

**Фактический сервер [API]:** во всех трёх методах поле отсутствует
(проба E12.3; совпадает с пробой E11). С учётом документированного условия
наличия это согласуется с интерпретацией E12.2: у тестового пользователя
(администратор) кода ограниченной роли не установлено → поле не
возвращается. Однако строгое доказательство «отсутствие ⇒ нет ограничения»
документацией не даётся — условие описывает, *когда* поле присутствует,
но не оговаривает явно семантику отсутствия.

**Сущность ограничения [Док+Вывод]:** формулировка «ограничение доступа»
+ «код ограниченной роли пользователя» указывает на связь
«пользователь × объект» (роль пользователя ограничивает доступ к данному
объекту). Привязка к конкретной операции (arm vs disarm) документацией не
раскрывается — **[Не установлено]**. Взаимодействие с `allowedActions`
(какой код проверяется при `objects/arm/`, что возвращает сервер при
ограничении) — **[Не установлено]** (проверка требует write-вызова).
Взаимодействие с `objects/arm/`/`objects/disarm/` в основном документе не
описано — **[Не установлено]**.

**Реализация E12.2 не менялась** (согласно ограничению задачи):
`restricted === 1` → `'no-permission'`, `restricted === 0` или отсутствие
→ продолжение проверок, прочие значения → `'unknown'`. Проба подтверждает,
что на текущем контуре поле всегда отсутствует и не влияет на вердикт —
обработка существует «в резерве» на случай объектов с ограничением роли.

## 4. Особенности IDP-объектов

Источники: `IDP REST API.docx` (сверено с docx), `Georitm REST API.docx`,
отчёты E8 (раздел 4), E11 (разделы 2, 4, 6), E12.1 (раздел 4).

1. **Что означает `isFromIDP=true` [Док]:** «Работа с объектом через IDP»
   — объект получает данные от прибора через приёмную подсистему IDP
   (`/idp-web/idp/rest/…`), которая транслирует протоколы приборов
   (Ademco Contact ID, Surgard, «Контакт», Bin и др.). Тестовый объект:
   `isFromIDP=true`, канал `channelControl: ["in_bin"]` (приёмный
   бинарный протокол) [API].
2. **Взаимодействие основного REST API с IDP-объектами [Не установлено]:**
   ни основной, ни IDP документ не описывает, исполняет ли основной API
   `objects/arm/` для IDP-объекта напрямую или транслирует команду в IDP.
   Совпадение схемы (`{imei, area}` → `{success: Integer}`) не доказывает
   совпадения поведения.
3. **Команды IDP API [Док]:** `objects/arm/` и `objects/disarm/`
   (`{imei: Long, area: Int}`): успех — `{success: 1}` («Успешное
   выполнение»); **прибор не на связи — единственный явно
   задокументированный отказ команды во всей документации**:
   `{"msg": "Command was declined by the device", "hdr": "Failed to submit
   the command", "data": null}` (HTTP-статус в IDP-доке не указан).
   Семантика IDP на основной API автоматически **не переносится**.
4. **Механизм подтверждения доставки команды [Док-отсутствие / Не
   установлено]:** поля «delivered/queued» в API не существуют (E11 4.3);
   `{success: 1}` в основном документе назван «Результат исполнения
   1-выполнено», но это противоречит наличию явного отказа в IDP —
   достоверно `{success: 1}` означает в лучшем случае «принято/передано»;
   фактическое исполнение прибором подтверждается только переходом
   `objects/state/` и событием журнала группы 4 (E11 4.2) — схема, уже
   реализованная в E12.
5. **Отказ прибора вне связи [Док, IDP; основной API — Не установлено]:**
   в IDP — синхронный отказ «Command was declined by the device»;
   в основном API форма ответа для offline-прибора не описана. Кабинет
   консервативно классифицирует явный HTTP-отказ как `rejected`, тайм-аут
   — как `unknown` (E12), что безопасно при любой из возможных форм.
6. **Ограничения для управления IDP-объектами [Не установлено / Вывод]:**
   для приёмных протоколов команда станции → прибор возможна не всегда
   (живая сессия прибора); в IDP есть отдельные механизмы запрета
   постановки (`objects/lock/`, `lock-state/`, `block/unblock/`) [Док],
   не проброшенные в основной API. Дополнительные ограничения команд для
   IDP-объектов основного API не документированы. Тестовый объект контура —
   именно IDP-объект, поэтому контрольная серия команд (E11 10.3) обязана
   начаться с него.

### 5.2. Использование реальных названий

Имя раздела (`partition.name`) и номер (`partition.num`) берутся из
серверных данных (DTO `PartitionControlState`), имя объекта — из пропса
`objectName` (RSC-снимок). Захардкоженных значений нет.

**Отклонение от буквы спецификации (не дефект безопасности):** требуемый
заголовок «Поставить зону 1 под охрану?» / «Снять зону 2 с охраны?»
реализован как «Поставить на охрану?» + отдельная строка «Раздел «Имя»
(№ N) объекта «X»». Информационное содержание то же (операция + реальное
имя/номер), но точная формулировка из задания не воспроизведена.

### 5.3. Найденные UX-дефекты (исправления не вносились — по ограничению E12.3)

1. **[Мелкий] Опечатка в заголовке диалога:** `ACTION_LABEL.disarm` =
   «Снять **с охрану**» (строка 44) — грамматически неверно; кнопка в
   строке раздела написана правильно («Снять с охраны»). В диалоге
   пользователь видит «Снять с охрану?».
2. **[Доступность] Нет перевода фокуса в диалог при открытии:** панель
   имеет `tabIndex={-1}`, но `focus()` не вызывается — скринридер и
   клавиатурный пользователь остаются на кнопке строки раздела, о
   появлении модального диалога фокус не сообщает.
3. **[Доступность] Нет focus trap:** фоновое содержимое (включая кнопки
   других разделов) остаётся в tab-порядке при открытом диалоге;
   клавиатурный пользователь может «за» диалогом открыть диалог другого
   раздела, заменив цель подтверждения (замена цели видима, дублирования
   API нет — дефект удобства, не безопасности).
4. **[Доступность] Escape и клик по оверлею не закрывают диалог** —
   безопасно для опасной операции (нет случайного подтверждения), но
   нестандартно; закрытие по Escape/оверею с семантикой «Отмена» было бы
   ожидаемым и безопасным.
5. **[Косметика] `running` вычисляется с избыточным условием**
   (`operation.action !== undefined` — всегда true); поведение корректно.

**Минимальные предлагаемые исправления (для отдельного этапа, не E12.3):**
опечатка «с охраны»; автозахват фокуса панелью при открытии; Escape +
клик по оверлею = `setConfirmTarget(null)`; focus trap (или хотя бы
`inert` на фоне); выравнивание заголовка с формулировкой спецификации
(«Поставить зону N под охрану?» — с реальными именем/номером). Все пять
изменений локальны в `object-control.ui.tsx` и не затрагивают сервер.

| 2a | Тип объекта | `objects-tree-set/` → `objType` | String '0'/'1' [Док] | высокая [Док+API] | не `'0'` → проходит дальше | `'0'` → `'unsupported'` | да |
| 2b | Поддержка объектом (`canArm`) | документирован в `obj/`, `obj-details/`; **в tree-set нет** | Boolean [Док] | **низкая: фактический сервер не возвращает** [API]; связь с проверкой write — [Не установлено] | `'unknown'` (запрет) | `false` → `'no-permission'`; некорректный тип → `'unknown'` | да, но признак недоступен из tree-set |
| 2c | Ограничение (`restricted`) | tree-set/obj/obj-details [Док] | Integer 1/0 [Док] | контракт документирован; фактически всегда отсутствует [API]; взаимодействие с arm — [Не установлено] | продолжение проверок (условное поле) | `1` → `'no-permission'`; прочее → `'unknown'` | да |
| 3 | Адресуемость раздела | `objects/obj-areas/` → `areas[].num` | Integer | высокая [Док+API, E11/E12.3] | раздела нет → 400 `unknown-area` до write | areaNum вне списка → отказ | да |
| 4 | Известность состояния | `objects/state/` по IMEI | карта `{num: 1|2}` | высокая [Док+API]; **но IMEI в prod-цепочке берётся из tree-set, где его нет** [API+Код] | `guarded=null`/нет карты → `'unknown'` | значение вне 1/2 → `'unknown'` | да |
| 5 | Допустимость в состоянии | кабинетная политика поверх `objects/state/` | boolean | политика кабинета (E11 8); серверное поведение — [Не установлено] | n/a | уже в целевом → 409 `already-in-state`, команда не отправляется | да |

**Итоговая оценка.** Модель структурно корректна: пять независимых
признаков, любое «неизвестно» запрещает, косвенные признаки (история
402.x, `allowedActions` без серверной пробы, IMEI, `isFromIDP`) не
разрешают управление. Однако **два признака из пяти в текущей прод-цепочке
недостижимы из-за источника данных (`ctx.target` = tree-set): `canArm`
(2b) и IMEI-зависимая известность состояния (4)** — реальный объект
всегда получит `'unknown'` независимо от ответов поставщика. Это не
дыра безопасности (запрет консервативен), а блокер доступности: данные
для признаков 2b и 4 существуют в `objects/obj/` (+ `objects/state/`
по его imei) и могут быть получены одним read-запросом обогащения.

**Предлагаемая целевая модель (без ослабления запретов):** обогатить
`ctx.target` read-вызовом `objects/obj/` для владеемого объекта
(imei, isFromIDP, потенциальные canArm/restricted) — тем же методом,
который уже используется `fetchOwnedObject` на пути страницы;capability
продолжает вычисляться только на сервере; отсутствие canArm остаётся
`'unknown'` до ответа P1. Дополнительно (E13): серверный аудит-журнал
команд (F8/E12.1).

## 7. Подтверждённые факты и неизвестные вопросы

**Подтверждено документацией [Док]:**
- `canArm` — Boolean, условное наличие, только `objects/obj/` и
  `objects/obj-details/`; в tree-set не документирован.
- `restricted` — Integer 1/0, «ограничение доступа», условие «если
  установлен код ограниченной роли пользователя», в tree-set/obj/obj-details.
- `isFromIDP` — «Работа с объектом через IDP».
- IDP arm/disarm: `{imei: Long, area: Int}` → `{success: 1}` или явный
  отказ «Command was declined by the device» при приборе вне связи.
- В основном документе arm/disarm: `{imei: String, area: Integer}` →
  `{success: Integer}` «Результат исполнения 1-выполнено»; ошибок метода
  не описано.

**Подтверждено фактическим сервером [API] (проба E12.3, 2.27.0, read-only):**
- tree-set для тестового объекта: ровно 6 полей; `canArm`, `restricted`,
  `imei`, `isFromIDP` отсутствуют.
- `obj/`: 12 полей, включая `imei` (строка длины 15) и `isFromIDP=true`;
  `canArm`, `restricted` отсутствуют.
- `obj-details/` (callDevice=false): 32 поля; `canArm`, `restricted`
  отсутствуют; `state: null`.
- `obj-areas/`: разделы `[0, 1]`; `objects/state/`: `{"1": 1}` —
  согласовано с E11.
- Повторно подтверждены наблюдения E11: отсутствие canArm у фактически
  управляемого объекта (история 402.3/402.1 от 2026-10-21).

**Подтверждено кодом [Код]:**
- Полный путь данных без преобразований; `ctx.target` — «сырая» запись
  tree-set; IMEI резолвится только из `ctx.target.imei`.
- Обогащённый объект страницы (`fetchOwnedObject`) получает imei из
  `obj/`, но в capability не используется.
- UX-гарантии диалога (раздел 5.1).

**Предположения [Вывод] (не факты):**
- «Отсутствие `restricted` означает отсутствие кода ограниченной роли» —
  согласуется с [Док] условием наличия и [API] наблюдением, но прямо не
  сформулировано документацией.
- «Основной API транслирует команду IDP-объекта в IDP» — правдоподобно,
  не доказано.
- «`restricted` блокирует обе операции (arm и disarm)» — интерпретация
  формулировки «ограничение доступа» без операционной привязки.

**Не удалось выполнить [Не установлено]:**
- Поведение `objects/arm/` при отсутствии права, при `restricted=1`, при
  offline-приборе, для `isFromIDP=true` — требует write-вызовов (запрещены).
- Фактическое заполнение `canArm`/`restricted` на объектах с ограниченной
  ролью и не-IDP объектах — на контуре один объект (IDP, admin).
- Семантика `{success: 1}` (принято/передано/исполнено) — только командой.
- Проверка диалога в реальном браузере (клик/клавиатура) — ревизия
  выполнена статическим анализом кода и стилей; поведенческие проверки
  (реальный double-click до ререндера, скринридер) не выполнялись.

## 8. Актуализированный список вопросов поставщику

Формулировки пригодны для отправки технической поддержке GEORITM.

**P1 (блокер допуска, уточнён).** Поле `canArm` документировано в ответах

## 10. Итоговая оценка готовности реального управления

**Feature gate остаётся выключенным.** Реальное управление (включение
gate) **не готово**; блокеры по сравнению с E12.2 не уменьшились и
уточнились:

1. **Источник данных capability не соответствует документации** (новое,
   подтверждено пробой): tree-set не содержит ни `canArm`, ни `imei` —
   в текущей цепочке реальный объект всегда `'unknown'` даже при
   идеальных правах. Требуется обогащение контекста (рекомендация 9.1) —
   это read-изменение, не ослабляющее запреты.
2. Ответы поставщика P1–P4 отсутствуют: семантика `canArm`/отсутствия,
   поведение IDP-объектов, `{success: 1}`, права — не подтверждены.
3. Аудит-журнал команд кабинета не реализован (F8).
4. Не выполнены проверка на не-администраторе и контрольная серия команд.

При этом **безопасность текущей реализации не нарушена**: все проверки
E12/E12.2 сохранены, неизвестные данные запрещают управление, gate
выключен, write-методы не вызывались ни разу. Управление остаётся
скрытым/заблокированным — «может скрывать доступное управление, но не
показывает запрещённое» (E11 3.1).
