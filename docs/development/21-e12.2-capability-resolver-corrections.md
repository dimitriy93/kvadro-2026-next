## 2. F1 (P1) — типизация и семантика canArm

**Причина дефекта.** Документация GEORITM описывает `canArm` как Boolean
(«Возможность управления постановки и снятия разделов стационарного объекта»,
«если есть данные»). Код E12 типизировал поле как `canArm?: 0 | 1` и
распознавал запрет только строгим сравнением `canArm === 0`. При фактическом
булевом `canArm: false` строгие сравнения не срабатывали ни в ветке запрета,
ни в ветке «неизвестно» (`canArm === undefined` — false), и функция возвращала
`'available'` — документированный запрет на уровне объекта игнорировался.

**Исправление** (по всему пути данных):

| Слой | Было | Стало |
|---|---|---|
| `lib/georitm/api-client.ts` (`GeoritmObjectSummary`) | `canArm?: 0 \| 1` | `canArm?: boolean` — Boolean по документации, с комментарием об истории дефекта |
| `lib/account/georitm-control.ts` (`computeControlAvailability`, вход) | `canArm: number \| undefined` | `canArm: boolean \| null \| undefined` |
| resolver, ветка запрета | `canArm === 0` → `'no-permission'` | `canArm === false` → `'no-permission'` |
| resolver, ветка «неизвестно» | `canArm === undefined` | `canArm !== true` — всё, кроме строгого `true` (`undefined`, `null`, `"true"`, `1`, `0`), даёт `'unknown'` |

Путь данных проверен: GEORITM response (JSON) → `callGeoritm` (JSON.parse,
без преобразований) → `objects-tree-set/` → `GeoritmObjectSummary` →
`ctx.target` → resolver. Нормализующего слоя, способного потерять или
преобразовать `false`, в цепочке нет; семантика теперь строга на всех этапах.
Приведения типов нет: распознаются только точные `true`/`false`.

**Итоговое поведение:**

| Значение `canArm` | Вердикт |
|---|---|
| `true` | положительный признак — остальные проверки продолжаются |
| `false` | `'no-permission'` — явный запрет |
| `undefined` | `'unknown'` — запрет |
| `null` | `'unknown'` — запрет |
| `"true"`, `1`, `0` | `'unknown'` — некорректный формат, запрет |

`canArm === true` не разрешает управление само по себе — все остальные
условия (право, restricted, IMEI, известность состояния) продолжают
проверяться (см. раздел «Комбинации» в тестах).

**Консервативная политика для отсутствующего `canArm` сохранена без
изменений** (F2): отсутствие поля → `'unknown'` → управление запрещено.
Возможность управления не выводится из IMEI, `allowedActions`, `isFromIDP`,
истории операций, событий 402.1/402.3 или наличия разделов — ни один из
этих признаков в resolver не добавлен.

**Ограничение по источнику данных (зафиксировано, не изменялось):** по
анализу REST-API (`GEO RITM/REST-API-ANALYSIS.md`, стр. 198/206) `canArm`
документирован в ответах `objects/obj/` и `objects/obj-details/`, но в
перечне полей `objs[]` ответа `objects/objects-tree-set/` (именно оттуда
берётся `ctx.target`) поле не перечислено. Если сервер не отдаёт `canArm`
в дереве, все объекты останутся в `'unknown'` — управление останется
заблокированным, что соответствует консервативной политике, но вопрос
«откуда кабинет получает canArm» входит в открытый вопрос поставщику P1.

## 3. F3 (P2) — исследование и обработка restricted

**Подтверждённый контракт** (извлечение из `Georitm REST API.docx`):

> `restricted` — **Integer** — «Ограничение доступа»: **1 — ограничен,
> 0 — не ограничен**; «Если установлен код ограниченной роли пользователя».

Это отличается от предполагаемой в задаче boolean-семантики
(`restricted === true/false`): документация определяет поле как Integer
со словарём 1/0. Реализована строго документированная семантика — boolean
и строковые значения считаются некорректным форматом (без приведения
типов), что в обоих прочтениях безопасно: и «некорректное значение», и
«запрет» блокируют управление.

**Обработка в resolver:**

| Значение `restricted` | Вердикт |
|---|---|
| `1` | `'no-permission'` — явный запрет «пользователь × объект» |
| `0` | ограничение не установлено — проверки продолжаются |
| отсутствует | ограничение не установлено — поле условное («если установлен код ограниченной роли»), отсутствие означает, что кода нет |
| `null`, `true`, `"1"`, `2`, … | `'unknown'` — контракт нарушен, запрет |

Обоснование трактовки отсутствия поля: (а) условие наличия в документации;
(б) проба E11 — у тестового объекта `restricted` отсутствовал, при этом
объект фактически ставился и снимался с охраны, т.е. отсутствие поля
наблюдалось у управляемого объекта. Риск этой трактовки (если сервер
скрывает поле при иных условиях) остаётся в открытом вопросе P7.

**Реализация:**
- `GeoritmObjectSummary.restricted?: number` — новое типизированное поле
  (Integer по документации; поле присутствует в выдаче `objects-tree-set/`,
  откуда берётся `ctx.target` — `REST-API-ANALYSIS.md`, стр. 206);
- `computeControlAvailability` принимает `restricted` и проверяет его
  независимо от `canArm` (разные измерения capability: ограничение доступа
  «пользователь × объект» против технической возможности объекта);
- оба места вызова (DTO `toPartitions` и решение о команде) передают
  `ctx.target.restricted` — DTO и решение не расходятся;
- `restricted: 1` при `canArm: true` даёт запрет — положительный `canArm`
  не перекрывает явное ограничение (проверено тестом).

**Неопределённости зафиксированы, поведение не придумано:** точное
взаимодействие `restricted` с `objects/arm/` (какой код `allowedActions`
проверяется, применяется ли ограничение к обеим операциям или к одной) —
открытый вопрос поставщику P7 (E12.1, раздел 7). Запрет при `1`
консервативен в обоих направлениях.

## 4. Судьба unknown-state (F5)

`ControlErrorReason 'unknown-state'` — мёртвое значение: grep по всему
репозиторию (включая UI, маршруты, клиентский код, тесты, документацию)
показал только два места — объявление в `contracts.ts` и запись
`'unknown-state': 409` в карте `REASON_STATUS` маршрута. Ни один
`ControlError` с этой причиной никогда не создавался: состояние раздела
«неизвестно» попадает в `'unknown'` capability → `'unknown-capability'`
(403). Публичные контракты не меняются: маршрут возвращает наружу только
человекочитаемое сообщение и флаг `controlDisabled`, машинная причина
причины `unknown-state` клиенту никогда не отправлялась; UI использует
только строковые вердикты `arm`/`disarm` (`=== 'available'`).

**Решение:** значение `'unknown-state'` удалено из `ControlErrorReason`
и из `REASON_STATUS` маршрута. Это не меняет ни один HTTP-ответ (причина
не достигалась), а составленность `REASON_STATUS: Record<ControlErrorReason, number>`
гарантирует, что карта и перечисление не разойдутся в будущем.

- Специального разрешения (или запрета) для `isFromIDP=true` **не
  реализовано** — поле в capability не участвует, как и в E12;

  до ответа поставщика GEORITM** (P1 — заполнение `canArm`, P2 —
  поведение команд основного API для IDP-объектов, P7 — семантика
  `restricted`); история событий 402.3/402.1 и `allowedActions` основанием
  для разрешения не являются.

  не входит в документированный перечень полей `objects-tree-set/` —
  источник `ctx.target`. Без ответа P1 (и, возможно, переключения
  источника признака на `objects/obj/`/`obj-details/`) класс объектов
  E11 останется заблокированным консервативным запретом.
