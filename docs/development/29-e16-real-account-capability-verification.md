## 2. Архитектура capability flow (аудит Этапа A)

Полная цепочка: `GEORITM → georitm-control enrichment → capability resolver → API DTO → UI`.

1. **Сессия.** `users/login/` → серверная сессия кабинета с Basic и проекцией прав `SessionControlPermissions` (`arm`/`disarm` — наличие кодов `objects.arm`/`objects.disarm` в `allowedActions`), `georitm-source.ts:180`.
2. **Владение.** `resolveGeoritmControlContext` (`georitm-source.ts:557`): объект должен присутствовать в выдаче `objects/objects-tree-set/` текущего пользователя; чужой/несуществующий → null (404).
3. **Обогащение (E13).** `enrichControlTarget` (`georitm-control.ts`): read-вызов `objects/obj/` по уже подтверждённому id, запись сверяется строго по `id`, переносятся только `imei`, `canArm`, `restricted` при фактическом наличии поля. Ошибка obj/ (кроме 401) — цель без обогащения → запрет; 401 отзывает сессию.
4. **Resolver.** `computeControlAvailability` (`georitm-control.ts:134`) — строгая семантика E12.2:
   - `canArm === true` — единственное положительное подтверждение; `false` — запрет; отсутствие/`null`/некорректный тип — `unknown` (безопасный отказ);
   - `restricted === 1` — запрет; `0`/отсутствие — ограничения нет; прочее — `unknown`;
   - отсутствие/пустой IMEI — `unknown`; раздел отсутствует в `objects/obj-areas/` — не адресуем; состояние из `objects/state/` вне словаря 1/2 или карта не получена — `guarded=null` → `unknown`;
   - `objType === '0'` (мобильный) — `unsupported`.
5. **DTO.** `getGeoritmControlState` → `ObjectControlState {enabled, availability, partitions[]}`; IMEI и внутренние идентификаторы в DTO не переносятся.
6. **Команда.** POST-маршрут: авторизация (401) → валидация `{action, areaNum}` (400) → gate (403, до ownership-чтений) → владение (404) → `executeObjectControl` (gate повторно) → `executeGeoritmControlCommand` (gate в третий раз, guard повторов) → **повторное** обогащение и повторное вычисление availability → только при `'available'` ровно один write-вызов.
7. **UI.** Кнопки только у разделов с `arm`/`disarm === 'available'`;capability вычислен сервером, клиент передаёт только `{action, areaNum}`.

## 6. Причина различия доступности

Единственное различающее capability-поле — **объектный `canArm` в `objects/obj/`**:

- Запись №1: `canArm` отсутствует → `computeControlAvailability` возвращает `unknown` (отсутствие поля не является разрешением, E12.2 F1) → управление запрещено консервативно.
- Запись №2: `canArm === true` + отсутствие `restricted=1` + разрешимый IMEI + раздел в `obj-areas/` + известное состояние `objects/state/` → `available` для разделов 1 и 2; раздел 0 отсутствует в карте состояний → `unknown` → скрыт.

Глобальные `allowedActions` у обеих записей идентичны (73 действия, включая `objects.arm`/`objects.disarm`, обе isAdmin) — глобальное право не отличает записи. Поведение кабинета определяется фактическими возможностями конкретной учётной записи на уровне конкретного объекта и раздела; тестовые данные и глобальные флаги на вердикт не влияют.

## 7. Найденные дефекты

**Дефект 1 (исправлен): Safe Preview при выключенном gate показывал декоративные кнопки без учёта capability.**

До E16 `getObjectControlState` при выключенном gate возвращал `{enabled: false}` без capability-данных, и UI для **обоих** реальных аккаунтов строил Safe Preview из DTO зон — учётная запись №1 (управление не разрешено) видела секцию «Управление охраной» с демонстрационными кнопками «Поставить на охрану» (подтверждение заблокировано, но элементы декоративные). Это противоречило требованию E16: видимость управления определялась глобальным флагом (gate), а не возможностями учётной записи.

**Дефект 2 (исправлен): рабочий режим объяснял причины недоступности вместо скрытия секции.**

При `availablePartitions.length === 0` рабочий режим показывал секцию с дифференцированной технической причиной (`no-permission`/`unsupported`/`unknown`). E16 требует: секция управления не отображается, причины и capability-флаги пользователю не показываются.

**Наблюдение (не дефект кабинета): `objType` приходит числом.**
На сервере 2.27.0 `objType` в tree-set/obj/ фактически number (`1`), хотя типизирован строкой. Проверка мобильных объектов (`objType === '0'`) на числовой `0` не сработала бы, но кабинет запрашивает только стационарные (`groupType=1`), и оба проверенных объекта стационарны. Зафиксировано как вопрос контракта поставщику; поведение для подключённых объектов корректно.

## 10. Остаточные риски и ограничения

1. **Gate выключен** (`GEORITM_CONTROL_ENABLED` не задан по требованию E16): реальных команд нет ни у одной записи; учётная запись №2 видит управление в режиме Safe Preview с честным демо-уведомлением. Рабочий режим с реальными кнопками активируется включением gate — отдельное решение, вне E16.
2. **`objType` типизирован строкой, сервер отдаёт number** — вопрос контракта поставщику (P-новый); на подключённых стационарных объектах не влияет.
3. **Видимость при `unknown`**: при временной ошибке GEORITM секция управления скрывается (без объяснений) — консервативное поведение E16; восстановление — обновлением страницы/опросом partitions.
4. `objects/obj-details/` не содержит `canArm`/`restricted`/`imei` на 2.27.0 — запасной источник capability недоступен; это учтено (enrichment только из obj/).
5. Кэш capability отсутствует: каждая страница/опрос пересчитывает разрешение (требование E16 выполняется ценой 3 read-вызовов на объект — в пределах допустимого).
6. Раздел 0 присутствует в `obj-areas/` обеих записей, но отсутствует в карте `objects/state/` — стабильно даёт `unknown` и не отображается; при появлении раздела 0 в state/ он отобразится по общим правилам.
