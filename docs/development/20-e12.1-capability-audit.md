## 1. Краткое резюме

1. **Главный вопрос задачи подтверждён:** для объекта-образца E11
   (стационарный, `isFromIDP=true`, фактически ставился и снимался с
   охраны — события 402.3/402.1, `canArm` **отсутствует**, `allowedActions`
   содержит `objects.arm` и `objects.disarm`) текущая реализация E12 даёт
   capability `'unknown'` → UI-кнопки скрыты, POST-команда отклоняется
   с 403 `unknown-capability` **[Проба]**. Управление законного (по
   косвенным данным) объекта блокируется консервативным запретом —
   это осознанное решение E11 3.1/E12, а не случайность, но в текущем
   виде оно заблокирует и реальные объекты того же класса.
2. **Обнаружен дефект типизации `canArm` (F1):** документация описывает
   поле как Boolean и в примере даёт `"canArm": true` [Док], код E12
   типизировал его как `0 | 1` и распознаёт запрет только по числовому
   `0`. При фактическом булевом `canArm: false` capability вычисляется
   как `'available'` — запрет управления на уровне объекта **не
   срабатывает** [Проба]. Требует исправления (раздел 8 — изменения кода
   описаны, но не внесены, ожидание согласования).
3. **Модель E12 безопасна, но одномерна:** единый `ControlAvailability`
   смешивает пять независимых признаков (право, поддержка объектом,
   адресуемость раздела, известность состояния, допустимость в состоянии).
   Предложена структурированная модель (раздел 4), которая делает каждый
   признак видимым и по отдельности доказуемым.
4. **`restricted` и `isFromIDP` не участвуют в capability.** `restricted`
   («ограничен кодом ограниченной роли») — документированный признак
   уровня «пользователь × объект» [Док], игнорируется (F3). `isFromIDP`
   игнорируется намеренно (семантика команд для IDP-объектов через
   основной API не документирована) — корректно по принципу «не
   додумывать», но должно быть закрыто ответом поставщика (F4, раздел 5).
5. **Безопасность E12 подтверждена по всем пунктам задачи** (раздел 6):
   ownership, серверный резолв IMEI/area, gate, защита повторов, отзыв
   сессии, отсутствие чувствительных полей в DTO, невозможность обхода
   capability клиентом.
6. **Готовность к E13:** техническая основа готова и безопасна; допуск
   реального управления блокируется тремя пунктами: дефект F1 (обязательное
   исправление), консервативный запрет при отсутствии `canArm` (F2 —
   требует ответов поставщика, сам по себе корректен) и неучёт `restricted`
   (F3). Изменения кода не внесены — ждут согласования (раздел 8).

## 2. Аудит текущего capability resolver (E12, `georitm-control.ts`)

Фактический алгоритм (`computeControlAvailability`, вызывается и для DTO
разделов, и повторно перед каждой командой — DTO и решение не расходятся)
[Код]:

| Шаг | Признак | Источник | Результат |
|---|---|---|---|
| 1 | feature gate | env `GEORITM_CONTROL_ENABLED` | off → `'disabled'` |
| 2 | тип объекта | `objType` из tree-set | `'0'` (мобильный) → `'unsupported'` |
| 3 | право пользователя | проекция `allowedActions` сессии (`objects.arm`/`objects.disarm`) | нет → `'no-permission'`; неизвестно (сессия до E12) → `'unknown'` |
| 4 | флаг объекта `canArm` | `objects/obj/` (tree-set/obj) | `0` → `'no-permission'`; отсутствует → `'unknown'` |
| 5 | IMEI | `target.imei` (владеемый объект) | отсутствует → `'unknown'`, `state/` не вызывается |
| 6 | адресуемость раздела | `objects/obj-areas/` | раздела нет → 400 `unknown-area` (до write) |
| 7 | известность состояния | `objects/state/` по IMEI | `guarded = null` → `'unknown'` |
| 8 | допустимость в состоянии | кабинетная политика | раздел уже в целевом → 409 `already-in-state` |

Проверка ключевой ситуации задачи (объект E11: stационарный, `canArm`
отсутствует, права есть, IMEI/разделы/состояние доступны) **[Проба]**:

```
canArm отсутствует  → 'unknown'   (кнопки скрыты; POST → 403 unknown-capability)
canArm = true (boolean) → 'available'
canArm = 1              → 'available'
canArm = 0              → 'no-permission'
canArm = false (boolean) → 'available'   ← ДЕФЕКТ F1
```

### Классификация признаков: разрешение, доступность или справка

| Признак | Чем является по документации | Достоверность связи с реальной проверкой сервера |
|---|---|---|
| `allowedActions` | «Коды разрешённых операций» пользователя [Док]; фактический каталог 73 кода получен (E8) | Права *пользователя*; **какой код проверяется при `objects/arm/` и что возвращается без права — [Не установлено]** (E11 3.3) |
| `canArm` | «Возможность управления постановки и снятия разделов стационарного объекта. **Если есть данные**» [Док] | Признак *технической возможности* уровня объекта с условным наличием: «если есть данные» прямо говорит, что отсутствие поля означает «данных нет», а не «нельзя». Связь с серверной проверкой — [Не установлено]. E11 425-строчный анализ («требуется canArm») — интерпретация аналитики, не документальное требование |
| `restricted` | «Ограничен кодом ограниченной роли» [Док] | Механизм «у одного пользователя действие на объект запрещено, у другого разрешено» (E11 3.2). Фактическое поведение — [Не установлено]; в E12 игнорируется |
| `isFromIDP` | «Работа с объектом через IDP» [Док] | Маршрутизация приёма данных; ограничения для команд *основного* API не документированы — [Не установлено] |
| IMEI, `obj-areas/`, `objects/state/` | Контракты подтверждены пробами E11 | Техническая адресуемость и состояние — высокая достоверность |
| События 402.x в журнале | Справочник группы 4 + реальный эпизод [API, E11] | **Только косвенное подтверждение прошлой управляемости** — по требованию задачи не может быть основанием для разрешения управления |

Вывод: из всех признаков только *адресуемость раздела* и *известность
состояния* подтверждены фактически; `allowedActions` и `canArm` —
правдоподобные, но недоказанные сигналы прав/возможности; `restricted` и
`isFromIDP` — недокументированные в контексте команд пробелы.

### Следствие для объекта-образца E11

Ситуация «объект успешно ставился/снимался + `canArm` отсутствует + права
в `allowedActions` есть» в текущей реализации → управление заблокировано
(`unknown`). Это консервативно **правильно** (задача запрещает разрешать
управление по косвенным признакам — журнал 402.x не доказывает, что
управление доступно именно этому пользователю кабинета), но в отчёте
зафиксировано явно: **текущая реализация заблокирует реальные объекты
этого класса**, и разблокировка возможна только через ответ поставщика
(вопрос P1, раздел 7) и контрольную серию команд (E11, раздел 10).

## 3. Предлагаемая модель: пять независимых признаков

Текущий единый `ControlAvailability` скрывает, *какой именно* признак
заблокировал операцию. Предлагается структурированный capability
(проект, не реализован):

```ts
interface PartitionCapability {
    /** 1. Право пользователя на операцию. */
    permission: 'granted' | 'denied' | 'unknown';
    /** 2. Техническая поддержка операции объектом. */
    support: 'supported' | 'unsupported' | 'unknown';
    /** 3. Возможность адресовать конкретный раздел. */
    addressable: boolean;
    /** 4. Известность текущего состояния охраны. */
    stateKnown: boolean;
    /** 5. Допустимость операции в текущем состоянии. */
    stateAllows: boolean;
}
```

| # | Признак | Источник | Достоверность | Действие при неизвестности |
|---|---|---|---|---|
| 1 | Право пользователя | `allowedActions` (login → проекция сессии) + `restricted` объекта | частичная: коды фактические [API], связь с проверкой write — [Не установлено] | `'unknown'` → блокировка; `restricted=true` при отсутствии данных о поведении → `permission: 'unknown'` |
| 2 | Поддержка объектом | `objType` [Док: метод для стационарных], `canArm` [Док, наличие условное], `isFromIDP` (решение — вопрос P2), тип канала `channelControl` [API, E11 3.5 — справочная информация] | `objType` — доказано; `canArm` — частично; `isFromIDP` — [Не установлено] | `'unknown'` → блокировка |
| 3 | Адресуемость раздела | `objects/obj-areas/` `areas[].num` | высокая [API] | раздел не найден → отказ 400 |
| 4 | Известность состояния | `objects/state/` (`1` снят / `2` под охраной) | высокая [API]; пробел: раздел 0 есть в obj-areas, отсутствует в карте (наблюдение E11) | `stateKnown: false` → блокировка |
| 5 | Допустимость в состоянии | кабинетная политика: «уже в целевом состоянии» (E11, раздел 8 — нецелевые воздействия); проверка alarm/fault на разделе — вопрос P5 | политика кабинета; серверное поведение — [Не установлено] | `stateAllows: false` → отказ 409 |

Принципы модели (соответствуют требованию задачи):

1. Признаки вычисляются независимо, и в DTO/UI видно, какой именно
   признак не подтверждён — «доступность управления не подтверждена»
   перестаёт быть неразличимым «unknown».
2. Операция разрешается только при **одновременном** подтверждении всех
   пяти признаков; любое `'unknown'`/`false` — блокировка.
3. Косвенные признаки (прошлые события 402.x в журнале, наличие права без
   доказательства серверной проверки) **не** переводят признак в
   «подтверждён» — только в списки для запроса поставщику.

## 4. Исследование IDP (без переноса семантики)

Изучены `IDP REST API.docx` (извлечение целиком) и разделы основного
документа (`objects/obj/`, `objects/arm/`, `users/login/`).

Подтверждено [Док, IDP]:

- IDP — отдельная подсистема приёма/трансляции данных от приборов
  (`/idp-web/idp/rest/…`), со своими пользователями, коннекторами
  протоколов (Ademco Contact ID, Surgard, «Контакт», Bin и др.) и
  сессиями приборов; Timestamp — миллисекунды; коды ошибок в документе
  не описаны (только 200).
- IDP `objects/arm/` и `objects/disarm/`: параметры `imei: Long,
  area: Int`; успешный ответ `{"success":1}`; **прибор не на связи** →
  `{"msg": "Command was declined by the device",
  "hdr": "Failed to submit the command", "data": null}` — единственный
  явно задокументированный отказ команды во всей документации.
- Основной API `objects/arm/`/`objects/disarm/`: `imei: String,
  area: Integer` → `{success: Integer}` «Результат исполнения 1-выполнено»;
  ошибок/ограничений для метода в основном документе **нет**.
- `isFromIDP: Boolean — «Работа с объектом через IDP»` — только
  описательное поле; **ни основная, ни IDP документация не описывает,
  как основной API исполняет команду для isFromIDP-объекта** (транслирует
  ли в IDP, какие ошибки возвращаются).

Выводы:

1. **Семантика IDP автоматически на `objects/arm/` основного API не
   переносится** — совпадает только схема параметров/ответа; поведение
   при приборе вне связи в основном API [Не установлено] (IDP-документ
   — единственный источник формы отказа, но его применимость к основному
   API не доказана).
2. Практическое значение для кабинета: тестовый объект контура —
   `isFromIDP=true` (E11) — т.е. класс объектов, для которых вся цепочка
   команд должна быть проверена первой, и в UI при включённом gate
   оправдано отдельное предупреждение «объект работает через приёмную
   подсистему; поведение команд не подтверждено» (решение — за E13 после
   ответа P2).
3. У объекта-образца канал — приёмный бинарный протокол
   (`channelControl: ["in_bin"]`, E11 3.5): команды станции → прибор
   для приёмных протоколов возможны не всегда — дополнительная
   информация, в capability E12 не участвует (правильно), вопрос P2
   закрывает и это.

## 6. Аудит безопасности E12 (коммит `cf20028`)

| Требование | Проверка | Результат |
|---|---|---|
| Ownership check | Маршрут: `findObjectForUser` до dispatcher; dispatcher: `resolveGeoritmControlContext` повторно проверяет объект в выдаче `objects-tree-set/` пользователя [Код] | ✓ двойная проверка; чужой и несуществующий объект неотличимы (404) |
| Защита от подмены objectId | `id` только из URL-параметра; никакого objectId из тела; GET/POST перепроверяют владение | ✓ |
| Серверное разрешение IMEI и area | Браузер передаёт только `{action, areaNum}` (валидация: действие — белый список, areaNum — целое 0…9999); IMEI резолвится только в `georitm-control` из владеемого объекта; раздел проверяется по `obj-areas/` | ✓ (смоук E12.3/4/15/21: точное тело запроса, IMEI отсутствует в DTO) |
| Feature gate | Двойная проверка (source.ts + первая строка команды); включение только `true`; ноль транспортных вызовов при off (смоук E12.14); demo подчиняется (E12.23); браузер повлиять не может | ✓ |
| Защита от повторных команд | `ControlCommandGuard`: 1 команда на «сессия×объект×раздел» (409 in-flight), rate 5/мин/сессия (429) [Код, смоук E12.13] | ✓; ограничение: реестр в памяти процесса — при нескольких экземплярах ослабевает (Amvera single-instance задокументировано) |
| Поведение после `unknown` | cooldown 120 с **на сервере** (409 cooldown) + UI блокирует кнопки до успешного опроса `partitions` (смоук E12.16) | ✓ |
| Отзыв сессии при 401 | `georitm-control` ловит `isUnauthorized` → `deleteSession` (существующий механизм), маршрут возвращает 401 (смоук E12.20) | ✓ |
| Чувствительные поля в DTO | `PartitionControlState` = {num, name, guarded, arm, disarm}; IMEI/внутренние id GEORITM отсутствуют (смоук E12.15 проверяет отсутствие IMEI в JSON) | ✓ |
| Отсутствие write-вызовов при выключенном gate | Смок E12.14 фиксирует ноль вызовов транспорта (включая read); `isGeoritmControlEnabled` вызывается при каждом обращении | ✓ |
| Обход capability клиентом | Клиент не передаёт capability; сервер пересчитывает её из живых данных при каждом вызове; прямой вызов API получает 400/403/409 по причине | ✓ невозможен |
| CSRF | Cookie `SameSite=Lax` + HttpOnly — кросс-сайтовый POST не несёт cookie | ✓ |
| Аудит команд | Журнал команд кабинета не реализован | ✗ — F8, задача для E13 |

## 9. Вывод о готовности к E13

**Техническая основа E12 готова и безопасна** — все требования задачи по
безопасности подтверждены кодом и смоук-сценариями, gate надёжно выключен.

**Допуск реального управления (включение gate) до E13 невозможен** без:

1. исправления F1 (дефект булева `canArm` — обязательное условие);
2. внесения F3 (`restricted` → консервативный запрет);
3. ответов поставщика P1–P8 (минимум P1, P2, P3, P4);
4. теста на не-администраторской учётке (E11, 10.2);
5. согласованной контрольной серии команд на тестовом контуре (E11, 10.3)

   E11;
6. реализации аудита-журнала команд кабинета (F8).

До выполнения этих условий текущее консервативное поведение

скрывать доступное управление, но не показывает запрещённое — что
соответствует принципу, зафиксированному в E11 3.1.
