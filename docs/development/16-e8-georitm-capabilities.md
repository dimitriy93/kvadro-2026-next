# E8 — GEORITM 2.27.0: карта возможностей и архитектурный план развития кабинета

**Проект:** kvadro-2026-next, личный кабинет клиента «Квадро-Арсенал»
**Дата:** 2026-11-15
**Статус:** исследовательская задача. Реализация функций, изменения UI/API/DTO/инфраструктуры и коммиты не выполнялись. Управляющие методы (`objects/arm/`, `objects/disarm/`, `objects/obj-scan/`, любые write-методы) не вызывались.

Условные обозначения достоверности:

- **[Док]** — подтверждено текстом документации (`Georitm REST API.docx`, `Описание формата отчетов.docx`, `IDP REST API.docx`).
- **[API]** — подтверждено фактическим ответом реального сервера 2.27.0 (read-only probe, тестовый контур, пользователь-администратор, 1 стационарный offline-объект).
- **[Код]** — обнаружено в коде существующей интеграции.
- **[Вывод]** — инженерный вывод из нескольких фактов.
- **[?] / [Не установлено]** — проверить не удалось; пробелов в знании не заполнять догадками.

Важно об ограничениях probe-прогона: тестовый пользователь имеет `isAdmin=1` (изоляция между обычными клиентами не проверялась), один стационарный объект offline, видеоподсистема/геозоны/планы на контуре, по всей видимости, не настроены. Факты `[API]` про «пустой ответ» могут означать как отсутствие функции у объекта, так и отсутствие настройки на контуре.

## 1. Краткое резюме возможностей GEORITM

1. **Ядро read-only покрыто документацией и подтверждено на реальном API**: список объектов пользователя (дерево групп), состояние объекта и разделов/зон, неисправности, журнал событий (последние 1000+1000 и за период), каналы связи, питание, температура, электросчётчик, изображения объекта (планы как картинки), координаты, справочник кодов событий (1206 шаблонов на сервере), отчёты json/pdf/excel.
2. **Реального времени нет.** Ни WebSocket, ни webhooks, ни SSE. Единственный push-механизм — OneSignal для мобильного приложения (`users/subscribe-push-notifications/`). Кабинет обязан работать опросом — текущая архитектура соответствует возможностям API.
3. **Управление охраной технически существует** (`objects/arm/`, `objects/disarm/`, ответ `{success:1}`), но **документация не позволяет отличить «команда принята» от «объект перешёл в состояние»**, полный список прав (`allowedActions`) не документирован, а фактическое поведение при отсутствии права неизвестно. IDP прямо показывает случай «Command was declined by the device». Управление остаётся функцией повышенного риска, требующей согласований.
4. **Видеонаблюдение**: в API есть только два метода `video-proxy/token/` и `video-proxy/cameras/` со **не раскрытой структурой камер**. На реальном контуре оба вернули `{}` (токен получить нельзя), поля `ru.ritm.has.mediaservers`/WebRTC-сигналинг в `users/login/` отсутствуют — **медиасервер на контуре не настроен**. Просмотр видео через кабинет на текущих данных нереализуем и требует проверки у поставщика.
5. **Карты и планы**: координаты объекта (`lat/lon` в `obj/`, `lbs/stat/`), геозоны с геометрией (`zones/`, `zones-groups/`), планы помещений — только как изображения (`pictures/find-for-object/` + `pictures/data/`, base64). Картографического сервиса в API нет — тайлы рисует фронтенд.
6. **Отчёты**: 28 типов в реестре `reports/` (основной документ) + 40 типов описано в «Формате отчётов» (+12 без реестра). Для охранного кабинета практически ценны **ALERTS, ALERTSUM (8 подтипов), OBJJOURNAL, OBJST, GUARDSCALLCOUNT, OBJSERVICE**, условно — ZONEVIZ/ACCESSCARD. Реестр `reports/` на 2.27.0 отвечает HTTP 400 — список типов придётся держать константой.
7. **Модель прав**: сервер фильтрует объекты по пользователю (подтверждено кодом и логикой API), права на операции — `allowedActions` из `users/login/`. На реальном сервере получен **полный фактический список кодов `allowedActions` (73 кода)**, включая `objects.arm`, `objects.disarm`, `alerts.close`, `alerts.closeall`, `objects.clearfaults`, `video.edit`, `control`, а также недокументированные поля `allowedAlertGroupIds` и `allowedAlertLogTypeIds`. Это закрывает вопрос C1 поставщику с фактической стороны и даёт основу модели capabilities.
8. **Документация противоречива и неполна** (единицы Timestamp, состав реестра отчётов, названия групп событий, опечатки параметров). Каждое противоречие зафиксировано в разделе 5; реальные форматы проверены probe-прогоном.

## 2. Аудит текущей интеграции

Текущая реализация (подтверждено [Код]) соответствует заявленной архитектуре и security-решениям; переписывание не требуется. Ключевое:

**Архитектура.** `Browser → UI (DTO) → API routes → source.ts (диспетчер demo|georitm) → georitm-source.ts → api-client.ts → GEORITM`. `lib/georitm/api-client.ts` реализует 11 методов: `users/login/`, `users/logout/`, `objects/objects-tree-set/`, `objects/obj/`, `objects/obj-card/`, `objects/get-status/`, `objects/state/`, `objects/obj-faults/`, `alert-template/list/`, `alerts/history-by-obj/`, `reports/{type}/{format}` (pdf/excel, бинарно).

**Безопасность.** Basic-токен GEORITM живёт только в серверном хранилище сессий (JSON-файл `/data/account-sessions`, ключ — SHA-256 от sessionId, TTL 8 ч, revocation при logout и любом 401); браузер получает только непрозрачный ID в HttpOnly-cookie. Ownership-check: разрешённый список объектов = выдача `objects-tree-set/` текущего пользователя; каждая операция проверяет объект по этому списку; чужой объект неотличим от несуществующего. Ошибки API не маскируются под норму (отсутствие `objectState` → `'fault'`; пустой список только при явном пустом успешном ответе).

**Классификаторы [Код].** `SecurityAlarmState` по приоритету alarm > fault > armed/partial/disarmed; `fireAlarm` всегда `'unknown'`; `connection` из `objectState.isOnline`/`isGsmOnline`; события классифицируются по группам справочника `alert-template/list/` (GROUP_TYPE: 1→security_alarm, 2→restored, 3→security_fault, 6→system), код "NNN.N"→NNNN (12/12 совпадений на реальном сервере); только 4 кода проверены фактически (402.1, 402.3, 761.1, 761.3), направление группы 4 — по подстрокам «снят»/«взят».

**Отчёты [Код]** — ALERTSUM и ALERTS pdf/excel: валидация периода (≤31 день, to не в будущем), лимиты конкуренции (1/пользователь, 2/процесс, честный 429), тайм-аут 30 с, лимит 25 МБ, `tzId: 'Europe/Moscow'`, `alertGroupId: [1..6]` только для ALERTS, стриминга нет (полное чтение в память).

**Скрытые ограничения [Код]**: тайм-аут 10 с на вызов; журнал каждый раз тянется целиком (`history-by-obj/`, без инкрементальности) и фильтруется/пагинируется на сервере рендера; in-memory rate-limit входа и кэш шаблонов (TTL 10 мин, 20 пользователей) не переживают рестарт; `groupType: 1` — в кабинет не попадают мобильные объекты; поля `area`/`areaZone` события отбрасываются — `zoneName` для реальных событий никогда не заполняется; координаты `lat/lon` из API не используются (страница карты работает без них).

**Что уже реализовано из матрицы возможностей:** авторизация, список объектов, состояние, карточка, зоны/разделы, диагностика (`obj-faults/`), оборудование (`obj/` → devices), журнал событий, ALERTSUM+ALERTS pdf/excel, разграничение доступа, PWA.

## 3. Разбор направлений

### 3.1. Управление охраной объекта

**Методы [Док]:**
- `objects/arm/` (`imei`: String, `area`: Integer) → `{success: 1}`; `objects/disarm/` — симметрично.
- Связанные: `objects/state/` (состояние разделов по IMEI: 1 снят / 2 под охраной), `objects/obj-scan/` (асинхронный опрос прибора: `partition.arm` 0/1), `objects/obj-areas/`, `objects/obj-details/` (`areas[].isGuarded`, `canArm`), `objects/get-csd-scan-allowed/` (модем), `objects/control-defaults/` (настройки контроля задержки входной зоны и др.), `checker/*` (КТС — телефонная проверка объекта через Asterisk, `check-result` → state 0 success/1 pending/2 failure/3 partial), `alerts/save-log/` (аудит-запись в журнал действий).

**Ключевой вопрос — различимость состояний команды. Установлено [Док]:**

| Шаг | Чем подтверждается | Достоверность |
|---|---|---|
| Команда принята сервером | HTTP 200 + `{success: 1}` | **[Док]**, но семантика `success` не расшифрована |
| Команда отправлена оборудованию | **Механизма нет.** Полей «delivered/queued» в API нет | [Не установлено] |
| Команда выполнена прибором | Косвенно: `objects/state/` / `obj-scan/` / `obj-areas/` показывают новый `arm`-статус; IDP прямо возвращает ошибку «Command was declined by the device» при приборе не на связи | **[Док, IDP]** для отказа; тайм-аут исполнения не документирован |
| Объект в нужном состоянии | Только последующий опрос состояния | **[Док]** |
| Ошибка/таймаут | Только по отсутствию перехода состояния; кодов ошибок arm/disarm нет | [Не установлено] |

**Ограничения и права [Док + API]:**
- `canArm` у стационарного объекта — «возможность управления постановки и снятия разделов» [Док]. **[API]**: для тестового объекта `canArm` в `obj-details/` **отсутствовал** (не `false`, а нет поля) — наличие/отсутствие поля, вероятно, зависит от типа прибора; трактовать отсутствие как «нельзя» или «неизвестно» — нужно решение.
- `allowedActions` содержит коды `objects.arm`, `objects.disarm`, `control` **[API]** — фактическое подтверждение существования прав на уровне пользователя. Какой код реально проверяется сервером при вызове `objects/arm/` — [Не установлено] (требует проверки, которая сама является управляющей).
- Поведение `objects/arm/` при отсутствии права (401/400/иное тело) — [Не установлено].
- Причины отказа на уровне зон: документация ограничений по зонам не содержит; единственные смежные механизмы — задержки входа/выхода (`control-defaults/enteringDelayControl`), битовые коды зон (`obj-scan`: 16 задержка на вход, 32 на выход) и IDP `objects/lock/` (запрет постановки на уровне прибора — IDP-метод, в основной API не проброшен).

**Вывод:** достоверный UX «команда принята → выполнена → объект в состоянии» реализуем только паттерном «отправили → опрашиваем `objects/state/`/`obj-areas/` до перехода или таймаута» с честной семантикой «статус не подтвердился». Успешный HTTP-ответ — не доказательство изменения состояния оборудования. Функция требует: ответов C1–C5 поставщика, разрешения, продуктового решения и отдельного плана проверок (соответствует решению, зафиксированному в `INTEGRATION-ROADMAP.md`).

### 3.2. Видеонаблюдение

**Что есть в API [Док]:**
- `video-proxy/token/` (`objectId`) → `{token, url}`; документировано: «Если токен не может быть получен, ответ будет пустым объектом».
- `video-proxy/cameras/` (`objectId`) → «список камер или пустой объект»; **структура камеры в документации не раскрыта (пример пустой)**.
- Косвенные признаки в `users/login/` [Док]: `ru.ritm.has.mediaservers` (Boolean), `ru.ritm.webrtc.signaling.server.host/port` — наличие WebRTC-сигналинга у инсталляции.

**Что показал реальный контур [API]:**
- `video-proxy/cameras/` → `{}`; `video-proxy/token/` → `{}` (токен получить нельзя).
- В ответе `users/login/` **поля `ru.ritm.has.mediaservers`, `ru.ritm.webrtc.*`, `canUseMapMatching`, `matching.service` отсутствуют** (в документации они есть). Интерпретация [Вывод]: сборка 2.27.0 отдаёт эти поля только при настроенной подсистеме; на контуре медиасервер не настроен.
- В `allowedActions` есть код `video.edit` [API] — право на *редактирование* видеонастроек; права на *просмотр* видеопотока не выявлены.

**Протоколы/форматы/CORS/браузерность** — в документации **нет ни слова**: ни HLS, ни RTSP, ни WebRTC-потока, ни структуры камеры, ни времени жизни токена, ни лимитов подключений. `url` в ответе token — это URL прокси-сервера (`http://my.proxy:8080/`), т.е. внешний компонент вне REST API.

**Оценка:** на текущих данных видеонаблюдение **не подтверждено** и нереализуемо. Направление требует отдельного опроса поставщика (структура камер, протокол, срок жизни токена, требования к сети) и, вероятно, отдельной инфраструктуры (медиасервер GEORITM + возможно прокси). В текущей Next.js-архитектуре реализуема только схема «backend запрашивает token+cameras, отдаёт DTO браузеру, браузер обращается к прокси GEORITM напрямую» — но: (а) прокси GEORITM должен быть доступен из интернета, (б) HTTPS/CORS прокси неизвестны, (в) credentials GEORITM в браузер при этом не передаются (только токен) — это плюс. Не утверждать поддержку видео, пока медиасервер не продемонстрирован.

### 3.3. Карты объектов и расположение зон

| Данные | Источник | Статус |
|---|---|---|
| Координаты объекта | `objects/obj/` / `obj-details/` (`lat/lon`), `objs-groups/tree-set` (`lat/lon` для стационарных) | **[Док]**; **[API]** для тестового объекта — отсутствуют в ответе `obj/` (объект без координат) |
| Координаты по GSM | `lbs/stat/` → `{position: {latitude, longitude, altitude, precision, type: "gsm"}}` | **[Док]**; **[API]** → HTTP 500 «Internal error … mobile.maps.yandex.net» — метод зависит от внешнего геосервиса Яндекса и на контуре деградировал |
| Адрес и геокодирование | Адресные поля стационарного объекта (country…appNumber, addressShort); `address/`, `address/find/`, `address/sources/` (YDX/GGL/ACH/OSM) | **[Док]**; **[API]** `address/sources/` → HTTP 500 — внешняя зависимость |
| Геозоны (географические) | `zones/` (type 0 полигональная / 1 радиальная, `points[] lat/lon`), `zones-groups/zones-tree/`, привязка к объектам `objects/get-zone-controls/` | **[Док]**; **[API]** zones-tree → 0 групп (геозон на контуре нет) |
| Планы помещений | `pictures/find-for-object/` → `[{fileName, caption, id, mimeType}]`, `pictures/data/` → base64 (внимание: параметры в query-string, ответ text) | **[Док]**, пример в доке с `caption: "План объекта"`; **[API]** для тестового объекта → `[]` (планов нет) |
| Векторных планов / привязки зон к координатам на плане | **Нет** | **[Док — отсутствие]** |
| POI-метки | `poi/*` — структуры не раскрыты (пустые примеры) | [Не установлено] |

**Выводы:**
1. Карта с расположением объектов — реализуема: координаты есть в API, тайловый провайдер (Яндекс/OSM) подбирается отдельно от GEORITM, принадлежность объектов проверена ownership-моделью. Ограничение: координаты заполнены не у всех объектов — UI обязан честно показывать «координаты не заданы» (это не ошибка API).
2. Карточка объекта с геопозицией — та же механика, дешевле.
3. План помещения с зонами — **только как картинка** (`pictures/`). Привязки охранной зоны-шлейфа (из `areas[].zones[]`) к координатам на картинке в GEORITM нет — интерактивную схему с состояниями отдельных зон на плане можно сделать только собственной оверлей-разметкой (данные о положении зон готовит оператор/админ вручную), GEORITM это не предоставляет.
4. Не подменять отсутствие координат/планов заглушками-иллюстрациями: состояние «не настроено» показывать явно.

### 3.4. Состояния, события и диагностика

**Уже используемые методы** (см. раздел 2) покрывают основу. Дополнительные возможности, подтверждённые документацией и/или реальным API:

| Возможность | Метод | Ценность для кабинета | Статус |
|---|---|---|---|
| Каналы связи: активный канал, SIM_1/SIM_2 (inserted/online/level 0–5/percent), LAN, WIFI | `channels/`, точечно `channels/level/` | «Состояние связи» в карточке объекта (уровень сигнала, вторая SIM) | **[Док]**; **[API]** → HTTP 400 для offline-объекта — поведение для offline-прибора уточнить (вероятно, требует связи с прибором) |
| Питание: основное/резервное, бортовое напряжение | `obj-details/` → `power {state 0/1, voltage}` (только мобильные) | Индикация питания | **[Док]**; для стационарных — питание через неисправности (301 сеть 220, 302 разряд АКБ) |
| Датчики температуры | `objects/temperature/` (`{датчик: {сенсор: t}}`, −128 = нет данных) | Доп. телеметрия | **[Док]**; **[API]** → HTTP 400 на контуре |
| Электросчётчик | `objects/el-meter-cnt/` → `{serialNum, t1..t4}`, ошибка → `{}` | Узкая ниша | **[Док]**; **[API]** → `{}` |
| Детальные состояния зон (тампер, батарея, КЗ, обрыв, нет связи, обход — битовые коды 1…8192) | `objects/obj-scan/` (асинхронный, scanState 0/1/2/3) | Значительно богаче `hasFault/hasAlarm`; но это **активный опрос прибора** — запрещённая категория без согласования | **[Док]**; **[API]** не вызывался (запрещено) |
| Последние неисправности с текстом сервера | `objects/obj-faults/` | Уже реализовано | **[API]**: 3 неисправности (301, 302, 308) |
| Список объектов в тревоге (с `isFireAlarm`, `isInProcess`, `guardArrived`, `guardCalled`) | `alerts/objects-in-alarm/`, `alerts/count-open-alarm-all/` | Дашборд «тревоги сейчас» | **[Док]**; **[API]**: count=0, список пуст |

### 3.6. Права доступа и доступность функций

**Как GEORITM определяет права [Док + API + Код]:**
- Доступ к объектам — серверная фильтрация по текущему пользователю во всех read-методах (дерево, obj/, отчёты, события). Проверка «объект не мой» невозможна через API иначе как по факту отсутствия в выдаче. Текущая реализация (ownership = presence in `objects-tree-set/`) — правильная и минимально достаточная.
- Права на операции — `allowedActions: String[]` в `users/login/`. **Фактический каталог с сервера 2.27.0 [API], 73 кода:** `reports.OBJSERVICE, objects.disarm, alarm.create, reports.SPEEDING, reports.FUEL2, reports.FULLALERTJOURNAL, staff.edit, reports.RUNMINI, users.edit, reports.OUTTEMP, reports.DISCRETEPARAMETERS, poi.edit, users.delete, poi.import, poi.delete, reports.ZONEVIZ, reports.ZONEVIZCOUNT, reports.FUEL, reports.DISTANCETOOBJECT, objectgroups.create, reports.CANDEVICERUN, alerts.closeall, alerts, alerts.edit, context.edit, reports.DEVTEMP, roles.edit, reports.OBJST, objects.delete, schedule.create, alerts.close, objects.shell, notifications, control.followed, reports.CARPOWER, users.edit.himself, objectgroups.edit, video.edit, reports.PASS, objects.status.edit, staff.create, geozones.assign, schedule.edit, reports.ZONEEX, poi.create, reports.ACCELERATION, zones.create, roles.delete, reports.MOVEPARK, objects.clearfaults, objects.arm, reports.FLOW, reports.DEVICERUN, roles.create, reports.LOSTFIX, reports.ENGSPEED, reports.OBJJOURNAL, schedule.delete, roles.bind, objects.create, zones.edit, reports.ALERTS, reports.COOLTEMP, reports.GUARDSCALLCOUNT, users.create, control, objects.edit, reports.DEVICE, reports.ACC, objectgroups.delete, staff.delete, reports.RUN, zones.delete`.
- **Недокументированные поля login [API]:** `allowedAlertGroupIds: [1..6]` (видимые группы событий) и `allowedAlertLogTypeIds: [2, -2]` (видимые типы записей журнала) — готовая основа фильтрации журнала по правам.
- Права на уровне объекта: `canArm` [Док], `restricted` («ограничен кодом ограниченной роли») [Док], `canControl` у выходов [Док].
- Группы геозон: явная привязка пользователь↔группа зон (`zones-groups/bind-to-user/`, `get-users/`) [Док].
- Группы объектов (`objs-groups/`) — иерархия группировки; привязка прав к группам объектов в API не описана [Док — отсутствие]; **[API]** корневая группа совпадает с именем пользователя — [Вывод] права на объекты выдаются через включение в группы, но механизм назначения в API не виден (администрирование вне REST).
- `users/children/` → HTTP 400 на контуре [API] — поведение для пользователя без дочерних не установлено.

**Что можно надёжно установить для пользователя/объекта:**
- доступность объекта — да (presence in tree);
- операции чтения — да (фактически всё читаемое доступно любому пользователю с доступом к объекту — других флагов в API нет);
- arm/disarm — по `canArm` + `allowedActions.objects.arm|disarm` — надёжность частичная: связь этих флагов с реальной проверкой сервера не подтверждена;
- отчёты — по кодам `reports.<TYPE>` в `allowedActions` [Вывод, высокая уверенность — список кодов совпадает с типами отчётов 1:1];
- видео — прав на просмотр не выявлено [Не установлено];
- закрытие тревог/сброс неисправностей — коды `alerts.close`, `alerts.closeall`, `objects.clearfaults` есть в каталоге [API], но это write-функции вне read-only-стратегии.

## 5. Подтверждённые и неподтверждённые возможности; расхождения документации и API

**Подтверждено полностью (Док+API):** авторизация Basic; read-ядро объектов/зон/событий; отчёты ALERTS/ALERTSUM/OBJST/OBJJOURNAL/GUARDSCALLCOUNT/OBJSERVICE в json (pdf/excel уже в проде кабинета); справочник 1206 шаблонов; каталог allowedActions; `objects/obj-faults/` (301/302/308); `{success:1}`-контракт arm/disarm на уровне схемы ответа (сам вызов не выполнялся).

**Частично подтверждено:** координаты объектов (есть в доке, на тестовом объекте не заданы); `lbs/stat/` (метод существует, деградирует из-за внешнего геосервиса); `channels/`, `temperature/` (HTTP 400 на offline-объекте — поведение при отсутствии связи не документировано); `video-proxy` (методы существуют, структуры пустые, медиасервер не настроен); `alerts/history-on-obj/` (200+пустой массив; единицы from/to окончательно не сверены); `users/children/` (HTTP 400 — не интерпретировано).

**Не подтверждено / не установлено:** видеопотоки (протоколы, HLS/RTSP/WebRTC, лимиты); просмотр камеры без передачи credentials (технически возможен через токен, но не доказан); план помещения как структурированная модель (нет — только картинки); векторные планы и привязка зон к плану (нет); время реакции ГБР (нет в API); причины снятия как отдельная сущность (нет); автоматический аудит-журнал действий пользователей (не описан); поведение `arm/disarm` при отсутствии права; тайм-аут исполнения команд; лимиты частоты запросов; срок жизни сессии/Basic; POI-структуры.

**Расхождения документации и фактического API (зафиксировано отдельно):**
1. Названия групп событий: доки «3 Снятие, Постановка / 5 Техническое» vs сервер «3 Неисправность / 4 Снятие / Взятие / 5 Системное» [API]. Текущий GROUP_TYPE в коде случайно корректен по номерам (1,2,3,6), но группу 4 в коде обрабатывают по подстрокам, а 5→system — фактически верно.
2. Реестр `reports/` на 2.27.0 отвечает HTTP 400; MOVEPARK заявлен в реестре, сервер отдаёт «unsupported reportType» [API].
3. `users/login/` на 2.27.0 не возвращает `canUseMapMatching`, `matching.service`, `ru.ritm.has.mediaservers`, WebRTC-поля из документации [API].
4. В `obj-details/` для тестового объекта нет `canArm`, нет `power`/`discrets`/`controls`/`ivideon` (мобильные поля), есть недокументированные `deviceControlOuts`, `devices[]`, `coutry` (опечатка) [API].
5. `objects/obj/` возвращает недокументированный массив `devices[]` с `shell`-URL внешних страниц прибора (device.ritm.ru) и `picture` [API].
6. `ObjectAlert` в `history-by-obj/` содержит поле `objStatus`, отсутствующее в доке; `receivedAt`/`alertTs` — мс; `lastGSMConnectionTime` — секунды [API]. Смешение единиц подтверждено per-field.
7. Неверный пароль → HTTP 500, а не 401 (зафиксировано ранее, подтверждено кодом интеграции) [Код].
8. `users/login/` содержит `allowedAlertGroupIds`/`allowedAlertLogTypeIds`, отсутствующие в доке [API].
9. `control-defaults/` на сервере шире документации: `connectionControl`, `panicButtonControl`, `channelControl`, `autoTestControl` [API].
10. Тело ответа `reports/OBJST/json` содержит пароль объекта (`pass`) [API] — при любом использовании фильтровать.

## 6. Модель прав и доступности функций (предложение capabilities-модели)

Единый серверный контракт «capability» (не реализовывать без согласования — предложение):

```ts
// Сервер вычисляет на уровне (пользователь, объект) — браузер получает только DTO.
type CapabilityAvailability =
  | 'available'      // 1. поддерживается и доступна
  | 'no-permission'  // 2. поддерживается, но нет прав
  | 'not-configured' // 3. не настроена для объекта (нет данных/настройки)
  | 'unsupported'    // 4. не поддерживается оборудованием/типом объекта
  | 'unknown'        // 5. невозможно определить
  ; // 6. «временно недоступна» — НЕ capability, а состояние вызова API

interface ObjectCapabilities {
  state:        Availability;   // состояние объекта
  zones:        Availability;   // разделы/зоны
  events:       Availability;   // журнал
  faults:       Availability;   // неисправности
  channels:     Availability;   // каналы связи (детально)
  power:        Availability;   // питание/резерв
  temperature:  Availability;
  coordinates:  Availability;   // карта
  floorPlan:    Availability;   // план (pictures)
  geozones:     Availability;
  video:        Availability;
  reports:      Partial<Record<ReportType, Availability>>;
  control:      {               // только как «видимость» функции, не готовность
    arm: Availability; detail: 'canArm' | 'allowedActions' | 'both' | 'unknown';
  };
}
```

Ключевые правила:
1. **Постоянная недоступность ≠ временная ошибка.** Capability вычисляется из источников, которые не зависят от сбоев: `allowedActions` (login), `canArm`/поля объекта, наличие координат/камер/планов в ответах API, тип объекта. Ошибка вызова GEORITM передаётся отдельно (HTTP-статус + деградация UI), capability не переключается в `unsupported` из-за таймаута — правило «ошибка API не маскируется под норму/отсутствие функции» продлевается на capabilities.
2. **Источники решения по типам:** (1) `available` — флаг в login/объекте + успешные данные; (2) `no-permission` — отсутствие кода в `allowedActions` / `canArm=false` (с оговоркой о недоказанности связи флагов и серверной проверки для arm/disarm); (3) `not-configured` — метод отвечает пустым результатом при валидном праве (`pictures: []`, `cameras: {}`, zones-tree пуст); (4) `unsupported` — поля семантически неприменимы к objType (мобильные поля у стационарного) или сервер вернул «unsupported reportType»; (5) `unknown` — поле отсутствует в ответе и семантика отсутствия неизвестна (случай `canArm`).
3. **Масштабирование:** capabilities вычисляются в `georitm-source.ts` (один слой, DTO-направление), UI рендерит по availability, новые функции добавляются как новые ключи `ObjectCapabilities` без переработки существующих. Для 40+ отчётов availability считается по `allowedActions['reports.<TYPE>']` + whitelist фактически поддержанных типов (реестр из API ненадёжен — держать константой).
4. Не доверять браузеру в выборе capabilities: всё вычисляется на сервере из фактических ответов GEORITM.

## 8. Архитектурные рекомендации

Сохраняются принципы: credentials только на сервере; DTO-only в браузер; ownership до любого запроса с objectId; чужой объект = несуществующий; ошибка API ≠ норма; отсутствие функции ≠ фиктивная норма.

1. **Все новые read-возможности ложатся в текущий `georitm-source.ts` + `api-client.ts`** — тонкие обёртки + маппинг в DTO, новых сервисов не требуется. Новый модуль нужен только для: (а) видеопрокси (если появится — отдельный proxy-handler с token-refresh, но это будущее поставщика); (б) долгоживущих планов/координат-кэшей, если объём станет заметным.
2. **Кэширование:** координаты/планы/справочники — серверный кэш с TTL (планы — часы, справочник шаблонов уже 10 мин); состояние/события — без кэша (как сейчас). Реестр отчётов — константа в коде (API ненадёжен), расширяемая.
3. **Инкрементальный журнал:** в `getGeoritmEventsForObject` заменить полную перезагрузку на `history-on-obj/` с курсором `from` (хранить в server-side кэше по паре session+object), падение → откат к полной загрузке `history-by-obj/`. Сначала сверить единицы `from/to` на контуре.
4. **Ошибки и тайм-ауты:** существующая схема (тайм-аут, классификация, 401→revocation) сохраняется; для `channels/`/`temperature/` добавить явную интерпретацию 400 при offline-приборе как «нет связи с прибором» (не «нет функции») — после подтверждения семантики у поставщика.
5. **Пагинация событий и объёмы:** оставшаяся боль — полная загрузка журнала; решается п.3, зависимостей от GEORITM не требует.
6. **Capabilities-модель** (раздел 6) — вычислять в `georitm-source.ts`, добавив DTO `objectCapabilities` к `MonitorObject` или отдельным endpoint'ом `/api/cabinet/objects/[id]/capabilities`.
7. **Карта:** тайлы — продуктовое решение (Яндекс/OSM); API-подход уже описан в ROADMAP (этап 8); никаких изменений инфраструктуры, ключ картографического провайдера — отдельная env-переменная.
8. **Что потребует инфраструктуры отдельно:** видео (медиасервер/прокси GEORITM, возможно отдельный relay), real-time (отсутствует в API), КТС (Asterisk).

## 9. Приоритетный roadmap

**Категория A — реализуется в текущей архитектуре, высокая ценность, низкий риск:**

1. **Каналы связи и питание в карточке объекта** (`channels/`) — «почему объект offline»: уровень сигнала, SIM_1/SIM_2, LAN. Сложность низкая, зависимость от связи с прибором — нужна обработка offline-случая. Ценность: клиент сам видит причину потери связи (частый звонок в пультовую).
2. **Инкрементальный журнал событий** (`history-on-obj/` + курсор) — устраняет главный технический долг (полная перезагрузка 1000+ записей на каждый запрос). Ценность: производительность и стабильность.
3. **Расширение отчётов:** OBJJOURNAL (глубокая история + действия дежурных) и подтипы ALERTSUM (connect/loss/220v/power) как «сводка состояния за месяц». Валидация как у существующих отчётов; для OBJST фильтровать `pass`.
4. **Карточка объекта: фото/планы из Pictures** — если у реальных объектов загружены планы; availability — `not-configured` при отсутствии. Средняя ценность, низкая сложность.

**Категория B — реализуемо, нужна продуктовая/поставщицкая доработка:**

5. **Карта объектов** (этап 8 ROADMAP): координаты из API + тайлы; предварительно — вопрос поставщику о заполненности координат и выбор провайдера. Ценность высокая, сложность средняя.
6. **Дашборд «объекты в тревоге»** (`alerts/objects-in-alarm/`) — простая, но ценность зависит от реальных сценариев клиента.
7. **Детальные состояния зон через `obj-scan/`** — после согласования частоты активного опроса приборов с поставщиком (запрещённая категория сейчас). Большая UX-ценность (тампер/батарея/нет связи по зонам).

**Категория C — нужна дополнительная проверка GEORITM:**

8. Видеонаблюдение — только после раскрытия поставщиком структур камер/протоколов и демонстрации настроенного медиасервера.
9. Ставка/снятие с охраны — после C1–C5, разрешения и отдельного плана безопасности (вне этого roadmap по решению, зафиксированному в INTEGRATION-ROADMAP.md).

**Категория D — нецелесообразно/невозможно на текущих данных:** real-time уведомления (нет в API), время реакции ГБР (нет в API), векторные планы с привязкой зон (нет в API), КТС через кабинет, транспортные отчёты.

**Рекомендуемая последовательность:** 1 → 2 → 3 → 4 → (параллельно) 5 → 6 → 7. Пункты 1, 2, 3 — чистое расширение существующих слоёв без изменения контрактов UI; каждый независим и откатывается изолированно.

## 10. Риски и вопросы, требующие решения владельца

**Риски:**
1. Тестовая учётка — администратор: изоляция между обычными клиентами не проверена на новых методах (alerts, отчёты по «чужим» объектам). Нужен тест на не-администраторе до production.
2. `arm/disarm`: связь `canArm`/`allowedActions` с реальной серверной проверкой не доказана; поведение при отсутствии права неизвестно.
3. Лимиты частоты запросов не документированы — расширение опроса (channels + журнал + отчёты) усиливает нагрузку; сохранять консервативные интервалы.
4. Внешние зависимости GEORITM деградируют (`lbs/stat` → Яндекс-геосервис, `address/sources` → 500) — не встраивать их в критический путь UI.
5. Секреты в ответах API (`pass` в OBJST, PASS/RESPONSIVE_PERSONS в obj-card/settings, эхо пароля в login) — фильтровать на сервере, не логировать.
6. Реестр отчётов ненадёжен — типы включать только после фактической проверки (пример MOVEPARK).

**Вопросы владельцу проекта (решения, а не факты):**
1. Согласовать состав этапа «Категория A» roadmap (п.1–4) — что реализуем первым.
2. Карта: выбор тайлового провайдера (Яндекс — условия лицензирования vs OSM) и budget на ключ.
3. Запросить у поставщика: структуру `video-proxy/cameras/`, наличие медиасервера в prod-инсталляции; семантику 400 у `channels/`/`temperature/` при offline-приборе; единицы `from/to` у `alerts/history-on-obj/`; поведение `arm/disarm` при отсутствии права (без вызовов — документационно); лимиты запросов; подтверждение названий групп событий (3/4/5) как канонических.
4. Согласовать capability-модель (раздел 6) как контракт до начала реализации пунктов roadmap.
5. Решить судьбу мобильных объектов (objType=0) — сейчас отсекаются `groupType: 1`; если у клиентов появятся мобильные объекты, кабинет их не покажет.
