## 1. Краткое резюме

1. **Контракт `objects/arm/` и `objects/disarm/` документирован полностью** (POST, `{imei: String, area: Integer}` → `{success: Integer}`), но фактическое поведение сервера не проверено и не может быть проверено без реальной команды. Критическая семантика `{success: 1}` противоречива: основной документ говорит «Результат исполнения 1-выполнено» (т.е. заявляет *исполнение*), IDP для аналогичных методов прямо приводит ошибку «Command was declined by the device» при приборе вне связи. Совмещая оба документа: `{success: 1}` означает, что сервер *принял и передал* команду; доказательства исполнения прибором ответ не содержит.
2. **Достоверное фактическое состояние охраны** — `objects/state/` по IMEI (по разделам: 1 снят / 2 под охраной), `objectState.isGuarded` и `areas[].isGuarded`. Эти источники согласованы между собой (проверено на реальном объекте). Единственное доказательство фактического исполнения команды — событие журнала с кодом группы 4 (постановка/снятие) от прибора и последующий переход состояния.
3. **Модель прав не замыкается.** `allowedActions` пользователя содержит коды `objects.arm` и `objects.disarm` [API], у объекта есть флаг `canArm` [Док], но: (а) связь этих флагов с реальной серверной проверкой `objects/arm/` не доказуема без вызова; (б) у тестового объекта, который **фактически брался и снимался с охраны** (события 402.3/402.1 от 2026-10-21 в журнале), поле `canArm` в `obj/` и `obj-details/` **отсутствует** — отсутствие поля не означает «управление невозможно».
4. **Справочник событий группы 4 (82 шаблона) получен целиком** [API]: подтверждены коды 402.1 «Снятие раздела с охраны» и 402.3 «Взятие раздела на охрану» (записи в реальном журнале совпадают со справочником посимвольно), и впервые зафиксированы коды **отказа оборудования**: 4501 «Ошибка снятия», 4503 «Ошибка взятия», 9201 «Неисправность при взятии на охрану», 4433 «Взятие на охрану с неисправностью» — они дают источник негативного подтверждения.
5. **Тестовый объект работает через IDP** (`isFromIDP: true`, прибор Contact GSM-14K, `channelControl: ["in_bin"]`) [API] — для объектов этого класса семантика команд может отличаться (приёмные протоколы допускают команды только при живой сессии прибора). Поведение `objects/arm/` для isFromIDP-объектов — [Не установлено].
6. **Попутно обнаружен латентный дефект** в `lib/georitm/api-client.ts`: `georitmObjectDetails` передаёт `objectId` скаляром, тогда как сервер 2.27.0 требует массив — скаляр даёт HTTP 500 «java.lang.Integer cannot be cast to java.util.Collection» [API]. Дефект сейчас недостижим (метод вызывается только для мобильных объектов, которых на контуре нет), но подлежит исправлению до любого использования `obj-details/` в E12.
7. Вывод: управление охраной технически реализуемо в текущей архитектуре по паттерну «команда → опрос состояния → событие журнала как подтверждение», но остаётся функцией повышенного риска: без ответов поставщика (C1–C5), проверки на не-администраторе и согласованного плана реальных команд на тестовом контуре реализацию начинать нельзя.

## 2. Точный контракт `objects/arm/` и `objects/disarm/`

Источники: «Georitm REST API.docx» (стр. 61–62 по оглавлению) [Док], «IDP REST API.docx» [Док], фактические read-only пробы контекста [API].

### 2.1. Основной API [Док]

| Свойство | `objects/arm/` | `objects/disarm/` |
|---|---|---|
| Назначение | «Взять раздел под охрану» | «Снять раздел с охрану» |
| HTTP-метод | POST (общее соглашение API — все методы POST) | POST |
| Endpoint | `/restapi/objects/arm/json` | `/restapi/objects/disarm/json` |
| Тело запроса | JSON: `{"imei": "863591025852785", "area": 2}` | то же |
| `imei` | String — IMEI прибора (обязательность в доке не помечена, но пример содержит оба параметра; без них поведение не документировано) | то же |
| `area` | Integer — номер раздела | то же |
| Ответ 200 | `{success: Integer}` — примечание в доке: «Результат исполнения 1-выполнено» | то же |
| Прочие значения `success` | не документированы (известен только смысл 1) | то же |
| Ошибки | общие для API: 401 (авторизация), 400 (параметры), 500 (прочие) с телом `{msg, hdr, data}`; отдельные коды для arm/disarm не документированы | то же |

Замечания к контракту:

1. **Идентификация — по IMEI, а не по objectId.** Вызывающая сторона обязана сама знать IMEI объекта; он есть в `objects/obj/` и в дереве объектов [Док+API]. В DTO кабинета IMEI не переносится [Код] — при реализации IMEI остаётся на сервере и резолвится там же из объекта после ownership-check.
2. **Команда адресуется разделу, а не объекту.** Номер раздела — `areas[].num` / ключ карты `objects/state/`. Нумерация разделов на реальном объекте не непрерывна: у тестового объекта есть раздел `num=0` (с зоной) и `num=1`, но карта `objects/state/` содержит только ключ `"1"` [API]. Валиден ли `area=0` для команды — [Не установлено]; вызовы для проверки запрещены.
3. **Обязательность параметров** в документации явно не помечена (таблица без колонки обязательности) — это общее свойство документации GEORITM [Док].
4. **Ответ при отказе оборудования в основном API не описан.** Аналогичные методы IDP прямо документируют: прибор не на связи → тело `{"msg": "Command was declined by the device", "hdr": "Failed to submit the command", "data": null}` [Док, IDP]. HTTP-статус этого ответа в IDP-доке не указан; применяется ли это поведение в основном API для isFromIDP-объектов — [Не установлено].
5. **«Не додумывать параметры»:** ни в основном документе, ни в IDP-доке нет параметров «все разделы», «задержка», «код подтверждения» и т.п. Контракт — ровно два поля.

### 2.2. Ограничения по типу объекта и оборудованию

- `canArm` — «Возможность управления постановки и снятия разделов **стационарного** объекта. Если есть данные» [Док]. Метод адресует разделы стационарного прибора; для мобильных объектов управление охраной через эти методы документацией не предусмотрено.
- **[API]** у тестового стационарного объекта `canArm` отсутствует и в `objects/obj/`, и в `objects/obj-details/` (не `false`, а нет поля) — при том, что объект фактически брался/снимался с охраны (события 402.x в журнале, раздел 5.3). Следствие: **отсутствие `canArm` ≠ невозможность управления**; трактовка отсутствия — отдельное решение (см. раздел 3, вопрос 1).
- **[API]** тестовый объект `isFromIDP: true`. Для IDP-объектов команда основного API, вероятно, транслируется в IDP (док это не описывает) — семантика и ограничения [Не установлено].
- Отдельных настроек объекта «разрешить дистанционное управление» в основном API не видно; в IDP есть `objects/lock/` (запрет постановки на уровне прибора) [Док], но в основной API он не проброшен.

### 2.3. Требования к правам

- Явно документированы только: `canArm` (объект), `canControl` (выходы) [Док]; `allowedActions` — «коды разрешённых операций» без перечня [Док].
- **[API]** фактический `allowedActions` администратора тестового контура содержит `objects.arm`, `objects.disarm`, `control`, `control.followed`, а также `alerts.close`, `alerts.closeall`, `objects.clearfaults`, `alarm.create` (полный каталог 73 кода — E8, раздел 3.6).
- **Какой код реально проверяется сервером при вызове `objects/arm/`** и что возвращается при его отсутствии — [Не установлено]: проверка требует вызова write-метода.

## 3. Права доступа и доступность управления (ответы на целевые вопросы)

### 3.1. Достаточно ли `objects.arm`/`objects.disarm` в `allowedActions` для показа кнопок?

**Нет оснований считать достаточным — и нет оснований считать необходимым.** [Вывод из фактов]

- `allowedActions` — права *пользователя* [Док]; у объекта есть отдельный `canArm` и `restricted` («ограничен кодом ограниченной роли») [Док] — модель, очевидно, двухуровневая: пользователь × объект.
- У тестового объекта `canArm` отсутствует [API] при реально работавшем управлении — т.е. пары «есть код в allowedActions + нет canArm» соответствует работающее управление (по крайней мере, управлением кто-то пользовался). Если бы существовала жёсткая связь «canArm=false → запрещено», она здесь нарушена.
- Практическое правило для E12 (консервативное, [Вывод]): показывать управление только при **одновременном** выполнении: (а) `allowedActions` содержит `objects.arm`/`objects.disarm`; (б) `canArm === true`, **если поле присутствует**; при отсутствии поля — состояние `unknown`, кнопки не показывать без положительного ответа поставщика. Это безопасный дефолт: он может скрыть доступное управление, но не покажет управление там, где оно запрещено.

### 3.2. Может ли действие быть разрешено пользователю глобально, но запрещено на конкретном объекте?

**Существование механизма правдоподобно, но не доказано.** [Вывод]

- Поля уровня объекта, пригодные для такого запрета: `canArm`, `restricted` [Док]. Механизм `restricted` описан как ограничение роли пользователя, а не объекта — т.е. это ровно случай «у одного пользователя действие на объект запрещено, у другого разрешено».
- У тестового объекта `restricted` отсутствует, `canArm` отсутствует [API]; у пользователя-администратора все права есть. Проверка реального запрета требует двух пользователей с разными правами — [Не установлено] (см. E8, риск 1: тестовая учётка — администратор).

### 3.3. Что возвращает GEORITM, если пользователь имеет право просмотра, но не управления?

**[Не установлено].** Ни один документированный сценарий это не раскрывает; возможные варианты (401, 400 с `{msg, hdr}`, 200 с `success != 1`) не отличимы без вызова. Для read-методов различий «просмотр без управления» на сервере не наблюдается — любой пользователь с доступом к объекту читает всё [API, E8]. Вопрос поставщику C1(в) остаётся открытым.

### 3.4. Как отличить отсутствие права от неподдерживаемой функции?

Готового механизма нет. Доступные различители [Код+Вывод]:

| Ситуация | Различитель | Достоверность |
|---|---|---|
| Метода нет на версии сервера | `isMethodMissing` (HTTP 400, тело `{"status":500,"message":"HTTP 404 Not Found"}`, стабильно при повторах) — сигнатура зафиксирована в E9 на `channels/` | [Код+API, E9] |
| Чужой/несуществующий объект (read-методы) | HTTP 401 «Invalid username or wrong password» — поэтому кабинет проверяет владение до вызова | [Код+API] |
| Нет права на write-метод | [Не установлено] | — |
| Функция не настроена для объекта | Предположительно пустой успешный ответ (как `obj-controls/` → `{}` на стационарном объекте [API]) — но для arm/disarm «пустого ответа» не бывает | — |

Важно: `objects/obj-controls/` — это **не права и не состояние охраны**, а «описание контролирующих входов прибора» (входы, `mobile object` в доке) [Док]. На стационарном тестовом объекте он вернул 200 `{}` [API] — для определения доступности arm/disarm непригоден; включён в пробу только чтобы закрыть вопрос «что это за метод».

### 3.5. Отдельные настройки объекта/оборудования/разделов, влияющие на управление

- `objects/control-defaults/` — серверные настройки контроля: фактически возвращает 5 блоков — `enteringDelayControl`, `connectionControl`, `panicButtonControl`, `channelControl`, `autoTestControl` [API] (документирован только `enteringDelayControl` [Док]). Влияют на *реакцию* станции (задержка входа, контроль связи), не на право команды.
- `enteringDelayControl.expectedAlerts = [4001, 4011, 4021, 4031, 4041, 4051, 4071, 4091, 4581]` [API] — сервер считает *снятие* подтверждённым по этим кодам журнала. Косвенное независимое подтверждение того, что событие 4021 (= «402.1») трактуется станцией как факт снятия.
- Задержки на вход/выход на уровне зон — биты 16/32 в `obj-scan/` [Док, метод запрещён]; запрет постановки — IDP `objects/lock/` [Док, не проброшен в основной API].
- Управляемость прибора может зависеть от канала: канал тестового объекта — приёмный бинарный протокол (`channelControl: ["in_bin"]`, isFromIDP) [API]; для приёмных протоколов команда станции → прибор возможна не всегда (IDP-док прямо описывает «Command was declined by the device») [Док]. Проверка по типам приборов — в раздел 11 (проверки перед разрешением).

## 4. Фактический результат команды: где подтверждение и как его читать

### 4.1. Где хранится фактическое состояние охраны

Три согласованных read-only источника [Док+API]; на тестовом объекте все три согласованы (раздел 1 снят, isGuarded=0, isGuarded=false):

| Источник | Гранулярность | Значения | Замечания |
|---|---|---|---|
| `objects/state/` (по `imei`) | раздел | `{"<num>": 1 снят / 2 под охраной}` | наиболее прямая «карта охраны по разделам»; на тестовом объекте вернул `{"state": {"1": 1}}` [API] |
| `objectState.isGuarded` (`objects/obj/`, дерево) | объект | 0 нет / 1 все / 2 частично | уже маппится в `SecurityAlarmState` [Код] |
| `areas[].isGuarded` (`objects/obj-areas/`, `obj-details/`) | раздел | boolean | `obj-areas/` отдаёт флаги всегда [API]; `obj-details/` отдаёт их только при `callDevice=true` (см. 6.2) |

Не годятся: `obj-scan/` — активный опрос прибора (запрещённая категория), `checker/status/` — КТС-подсистема (не исследовалась, категория write-рисков), `obj-controls/` — входы прибора (см. 3.4).

### 4.2. Как подтвердить фактическое выполнение команды

Механизма подтверждения доставки/исполнения в API **нет**. Цепочка достоверности строится только косвенно [Вывод, соответствует E8 3.1 и дополнена новыми фактами]:

1. **HTTP 200 + `{success: 1}`** — команда принята сервером (в лучшем случае — передана прибору). Документ основной API формулирует «Результат исполнения 1-выполнено» [Док], но это противоречит наличию в IDP отдельного явного отказа «Command was declined by the device» [Док] и не может считаться доказательством исполнения. **На реальном сервере семантика не проверена** [Не установлено] — и не может быть проверена без команды.
2. **Событие журнала группы 4 от прибора** — единственное свидетельство того, что прибор команду исполнил: 402.3 «Взятие раздела на охрану» / 402.1 «Снятие раздела с охраны» (и родственные, см. 5). Подтверждено на реальных данных: события в журнале тестового объекта совпадают со справочником посимвольно [API]. Код события независим от того, кем выдана команда (кнопкой, ключом, дистанционно) — источник команды по коду 402.x не определяется.
3. **Переход состояния** — `objects/state/`/`isGuarded`/`isGuarded` раздела меняются согласованно [Док+API]. Скорость перехода после команды — [Не установлено] (измеряется только реальной командой).
4. **Отказ оборудования** — журнальные коды ошибки взятия/снятия (см. 5) и отсутствие перехода состояния до тайм-аута. Плюс возможный синхронный отказ «Command was declined by the device» (гарантирован только для IDP [Док]).

Схема подтверждения для E12 (минимально достаточная, [Вывод]):

```
команда → HTTP 200 {success:1} = «принято сервером» (не более)
       → опрос objects/state/ каждые 2–3 с, окно ≤ 60–90 с
       → параллельно смотреть журнал на коды группы 4 (402.x — успех; 4501/4503/9201 — отказ)
       → переход в целевое состояние + событие = «выполнено»
       → отказ-код = «отклонено»
       → ни того, ни другого до конца окна = «результат неизвестен»
```

### 4.3. Различимые ситуации

| Ситуация | Признак | Достоверность |
|---|---|---|
| Сервер отклонил вызов (права/параметры) | HTTP 400/401/500 с `{msg, hdr}` — фактическая форма для случая «нет права» неизвестна | [Док общая; форма при отсутствии права — Не установлено] |
| Прибор вне связи, команда не передана | `{"msg":"Command was declined by the device","hdr":"Failed to submit the command"}` — прямо задокументировано в IDP; статус и применимость в основном API — [Не установлено] | [Док, IDP] |
| Команда передана, прибор не исполнил | коды 4501/4503/9201 в журнале и/или отсутствие перехода состояния | [API справочник; поведение — Не установлено] |
| Команда исполнена | 402.x (или родственные) в журнале + переход состояния | [API, события подтверждены на реальных данных] |
| Команда в очереди (отдельный статус) | **Нет в API** — поля «delivered/queued» не существуют | [Док — отсутствие] |

### 4.4. Что происходит в журнале при успешной постановке и снятии

### 6.2. Новые факты относительно E8

1. **`objects/obj-details/` требует `objectId` массивом.** Скаляр → HTTP 500 `msg: "Internal error. See server logs: java.lang.Integer cannot be cast to java.util.Collection"` [API]. Массив → 200. 2. **`callDevice` меняет состав ответа больше, чем «ходить ли на прибор»:** при `callDevice=false` поля `areas[].isGuarded/hasFault/hasAlarm` и флаги зон **отсутствуют**; при `callDevice=true` — присутствуют [API] (прибор при этом offline — т.е. флаги берутся из БД станции, но материализуются только в «полной» ветке). 5. **Полный справочник группы 4** (82 шаблона) и коды отказа команды — впервые (раздел 5).
6. **Реальный эпизод 402.3→402.1** на тестовом объекте (2026-10-21) — фактический образец журнала при успешных команде/снятии (раздел 4.4).

## 8. Предлагаемый UX (минимальный, E12)

Принципы: не показывать управление без подтверждённой доступности; не выдавать `{success:1}` за исполнение; никогда не повторять команду вслепую; состояние охраны — только от сервера.

**Размещение:** страница объекта (карточка состояния охраны). Управление **по разделам** (контракт — `imei + area`); кнопка уровня объекта допустима только когда раздел один. Имена разделов — как в списке разделов.

**Состояния кнопки/операции:**

1. **Доступна** (idle) — capability `available` (см. раздел 3.1); видны обе кнопки или одна по текущему состоянию раздела.
2. **Подтверждение** — диалог: «Снять с охраны раздел <имя> объекта <имя>?» / «Поставить на охрану…»; подтверждение обязательно для обоих направлений (снятие убирает защиту, взятие может вызвать тревогу при людях внутри).
3. **Выполняется** — индикатор отправки; обе кнопки раздела и объектные заблокированы; повторное нажатие невозможно.
4. **Выполнено** — фактическое состояние раздела стало целевым (переход в `objects/state/`); UI обновляет состояние из обычного источника данных (не из клиентского кэша).
5. **Отклонено** — явный отказ сервера (400/401/500 с сообщением) или отказ-код журнала (4501/4503/9201); показать текст сервера без технических деталей.
6. **Результат неизвестен** — окно наблюдения (60–90 с) истекло без перехода и без отказа: явно показать «Команда принята сервером, но подтверждение не получено. Проверьте состояние объекта перед повтором».
7. **Недоступно** — `no-permission`/`unsupported`/`unknown` capability: кнопки скрыты; при `unknown` — пояснение «доступность управления не подтверждена».

**Обновление состояния:** во время операции — опрос сервера кабинета каждые 2–3 с до 90 с; вне операции — обычная частота страницы. Истина — только ответ сервера кабинета (который читает `objects/state/`); клиентский кэш/RSC-снимок не источник истины [соответствует архитектурным требованиям].

**Повторная отправка после тайм-аута — отдельный сценарий:** перед повтором UI обязан запросить фактическое состояние; повторное взятие уже взятого раздела и повторное снятие уже снятого — нецелевые воздействия. Минимально: при «Результат неизвестен» кнопки остаются заблокированными до следующего успешного опроса состояния, после которого UI показывает актуальное состояние и снова вычисляет доступные действия.

**Не предлагается в E12:** управление группой объектов, повторная отправка по тайм-ауту «в один клик», отображение успеха по `{success:1}`, управление при offline-объекте без отдельного предупреждения (прибор вне связи — вероятный отказ; предупредить, но не блокировать жёстко — семантика не подтверждена).

## 9. Предлагаемая архитектура E12 (описание, код не пишется)

Сохраняются принципы E8/E10: credentials только на сервере; DTO-only в браузер; ownership-check до любого запроса с objectId; ошибка API ≠ норма; отсутствие функции ≠ фиктивная норма.

### 9.1. Слои

```
UI (страница объекта)                — кнопки по capability + операционные состояния
        │ fetch (JSON)
POST /api/cabinet/objects/[id]/control        — orchestrator: capability → команда
GET  /api/cabinet/objects/[id]/partitions     — read-only опрос состояния разделов (новый)
        │
source.ts (диспетчер demo|georitm)   — armObject / disarmObject / getPartitions + demo-аналоги
        │
georitm-source.ts                    — ownership, capability, резолв imei, маппинг
        │
api-client.ts                        — тонкие обёртки georitmArm/georitmDisarm/georitmPartitionsState
```

### 9.2. Ключевые решения

1. **Capability на сервере.** При логине сохранять в запись сессии серверного хранилища проекцию `allowedActions` (флаги `canArm`/`canDisarm` пользователя — вычисляются один раз) [Код-план: сейчас session-store хранит только basic+user]. На уровне объекта capability вычисляется в `georitm-source` из `allowedActions` (сессия) + `canArm` (obj/, если поле есть) → `ObjectControlCapabilities = {arm: Availability, disarm: Availability}` в DTO объекта. Отсутствие `canArm` → `unknown` (консервативно: кнопки скрыты), до ответа поставщика.
2. **Команда — один endpoint, действие в теле.** `{action: 'arm'|'disarm', areaNum: number}`; валидация action и areaNum белым списком; **imei резолвится на сервере** из владеемого объекта (в браузер не передаётся и из браузера не принимается) [соответствует контракту «imei не включён в DTO»].
3. **Ограничения перед вызовом:** объект в выдаче tree-set текущего пользователя; capability `available`; не более одной in-flight команды на пару (session, object); глобальный лимит команд в минуту (защита от циклов); повторный вызов во время «неизвестного результата» отклоняется сервером (HTTP 409-подобный ответ DTO), а не только UI-блокировкой.
4. **Ответ команды — честная трёхзначность:** `accepted` (HTTP 200 + success=1) / `rejected` (явный отказ с текстом сервера) / `error` (сеть, тайм-аут, 5xx). Поле «исполнено» в ответе команды отсутствует по определению API.
5. **Подтверждение — отдельный read-only endpoint** `partitions` (обёртка `objects/state/` по imei объекта + fallback на `obj-areas/`): UI опрашивает его в окне наблюдения; совместный признак «выполнено» = переход состояния (+ опционально событие группы 4 в журнале). Ошибки опроса не превращаются в «выполнено/отклонено» — продлевают окно до тайм-аута.
6. **Классификатор журнала расширяется минимально:** в `VERIFIED_CODES` добавить отказ-коды 4501/4503/9201 (и родственные) как отдельные типы событий (`security_arm_failed`/`security_disarm_failed`) — только после подтверждения семантики поставщиком; до того — не интерпретировать.
7. **Аудит на стороне кабинета:** серверный журнал (кто, когда, объект, раздел, действие, результат команды) — обязателен; запись через `alerts/save-log/` — только после ответа на C4 (это write-метод).
8. **Demo-источник** получает те же три функции (arm/disarm/partitions) на фиктивных данных — для тестов UI без реального оборудования.
9. **Не делать:** клиентские таймеры как источник истины; автоматические ретраи команды; кэширование `objects/state/` (только живой опрос).

### 9.3. Обязательные пред-исправления в существующем коде

- `georitmObjectDetails` — передавать `objectId: [id]` массивом (раздел 6.2.1) — сделать **до** любых новых использований `obj-details/`.
