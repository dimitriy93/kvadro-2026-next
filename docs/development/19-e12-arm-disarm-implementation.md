# E12 — Реализация управления охраной под жёстким запретом (feature gate)

**Проект:** kvadro-2026-next, личный кабинет клиента «Квадро-Арсенал»
**Дата:** 2026-11-15
**Статус:** реализация завершена и закоммичена. Реальная отправка команд
(`objects/arm/`, `objects/disarm/`) **не выполнялась ни разу** — ни на
тестовом контуре, ни на каком-либо другом: feature gate выключен во всех
окружениях, все проверки выполнены на mock/fake транспорте и demo-данных.

## 1. Итог

Техническая основа управления охраной реализована полностью и остаётся
**выключенной**: серверный feature gate `GEORITM_CONTROL_ENABLED` не задан
ни в одном окружении (`.env.example` — пустое значение, Amvera — переменная
не задана, `.env.local` — переменная отсутствует). При выключенном gate:

- `POST /api/cabinet/objects/[id]/control` возвращает 403 с пометкой
  `controlDisabled: true` и выполняет **ноль** обращений к GEORITM
  (проверено smoke-сценарием: не выполняется ни read-, ни write-вызов);
- `GET /api/cabinet/objects/[id]/partitions` возвращает `{enabled: false}`
  без обращений к источнику;
- UI не рендерит секцию управления вовсе — у пользователя не создаётся
  впечатления, что он может управлять объектом;
- demo-источник подчиняется тому же gate (обход запрещён и проверен тестом).

Включение gate возможно только значением ровно `'true'` и только после
проверок раздела 9 (ответы поставщика, не-администраторская учётка,
согласованная серия команд на тестовом контуре).

## 2. Архитектура

Слои соответствуют предложению E11 (раздел 9) и соглашениям проекта:

```
UI (страница объекта, client-компонент object-control.ui.tsx)
        │ fetch JSON {action, areaNum}          ← браузер передаёт только это
POST /api/cabinet/objects/[id]/control          — команда + наблюдение результата
GET  /api/cabinet/objects/[id]/partitions       — read-only опрос состояния разделов
        │
source.ts (диспетчер demo|georitm)              — getObjectControlState / executeObjectControl
        │
georitm-control.ts                              — capability, резолв imei/разделов, команда
        │
control-engine.ts (чистый движок)               — наблюдение результата, guard повторов
        │
api-client.ts                                   — georitmArm/georitmDisarm/georitmObjectAreas
```

- `lib/account/control-gate.ts` — парсер feature gate, без зависимостей.
- `lib/account/control-engine.ts` — чистый движок (паттерн event-journal):
  транспорт, часы и паузы инъецируются, поэтому все сценарии «команда →
  опрос состояния → журнал» прогоняются smoke-скриптом без сети.
- `lib/account/georitm-control.ts` — серверный модуль управления: порядок
  проверок фиксирован (gate → guard → владение (выше, в georitm-source) →
  разрешение раздела/IMEI → доступность → команда → наблюдение); не
  импортирует Next.js — тестируется напрямую.
- `lib/account/demo-control.ts` — demo-аналог с тем же gate и теми же
  инвариантами (владение, запрет при неизвестном состоянии, отказ при
  разделе в целевом состоянии).
- `lib/georitm/api-client.ts` — тонкие обёртки: `georitmArm`,
  `georitmDisarm` (write, помечены в docstrings как вызываемые только
  из georitm-control за gate), `georitmObjectAreas` (read-only).

## 3. Пред-исправление: дефект `georitmObjectDetails` (E11, 6.2.1)

`objects/obj-details/` на сервере 2.27.0 требует `objectId` **массивом**;
скаляр даёт HTTP 500 «java.lang.Integer cannot be cast to
java.util.Collection». Исправлено: `{objectId: [objectId], callDevice: false}`.
Гарантия сериализации — smoke-сценарий E12.5 (mock fetch, точное тело
запроса). Другие методы не затронуты; семантика DTO не менялась.

## 4. API-контракты

### POST `/api/cabinet/objects/[id]/control`

Тело: `{"action": "arm"|"disarm", "areaNum": <integer 0..9999>}` —
**IMEI и внутренние идентификаторы GEORITM браузером не передаются и
не принимаются**; они разрешаются только на сервере.

Успех 200 (no-store):

```json
{"success": true, "result": "confirmed|rejected|unknown", "message": "...", "partitions": [...]}
```

Отказы (все с `Cache-Control: no-store`): 400 — некорректное тело/чужой
раздел (`unknown-area`); 401 — нет сессии или 401 GEORITM (сессия отозвана
существующим механизмом); 403 — gate выключен (`controlDisabled: true`),
нет права, не поддерживается, доступность не подтверждена; 404 — объект
не владеется; 409 — раздел в целевом состоянии (`already-in-state`),
команда уже выполняется (`in-flight`), cooldown после неизвестного
результата (`cooldown`), состояние раздела неизвестно; 429 — лимит частоты;
502/504 — недоступность GEORITM.

### GET `/api/cabinet/objects/[id]/partitions`

DTO `ObjectControlState`: `{enabled, availability, partitions[]}`, раздел —
`{num, name, guarded: true|false|null, arm, disarm}`. `guarded: null` —
состояние достоверно неизвестно (команда при этом запрещена). Имя и номер
раздела — из `objects/obj-areas/`; IMEI в DTO не переносится.

### Типы DTO (contracts.ts)

`ControlAction`, `ControlAvailability` (`available | no-permission |
unsupported | disabled | unknown`), `PartitionControlState`,
`ObjectControlState`, `ControlResult` (`confirmed | rejected | unknown`),
`ControlOperationResult`, `ControlErrorReason`, `ControlError`.

## 5. Алгоритм разрешения объекта и раздела (сервер)

1. Сессия пользователя (`getSessionUser`) → `resolveGeoritmControlContext`
   (georitm-source): объект **обязан** быть в выдаче `objects-tree-set/`
   текущего пользователя — владение подтверждается **до любого** обращения
   к GEORITM с идентификаторами объекта (включая резолв IMEI); чужой и
   несуществующий объект неотличимы (404).
2. Разделы — `objects/obj-areas/` (read-only, подтверждён E11): раздел
   команды обязан присутствовать в ответе (`areas[].num`); `areaNum` вне
   списка → `unknown-area`, write-метод не вызывается.
3. IMEI — `target.imei` из владеемого объекта; отсутствует/пуст →
   capability `unknown`, `objects/state/` по такому объекту не вызывается.
4. Доступность действия — `computeControlAvailability` (единая функция для
   DTO и решения о команде, поэтому DTO и решение не расходятся):
   - gate выключен → `disabled`;
   - `objType === '0'` (мобильный) → `unsupported` (метод документирован
     для стационарных, E11 2.2);
   - право отсутствует в проекции `allowedActions` сессии
     (`objects.arm`/`objects.disarm`) или `canArm === 0` → `no-permission`;
   - `canArm` **отсутствует** у объекта или права неизвестны (сессия
     до E12) → `unknown` — консервативный запрет (E11 3.1): может скрыть
     доступное управление, но не покажет запрещённое;
   - IMEI не разрешён или `guarded === null` (состояние неизвестно) →
     `unknown`;
   - иначе `available`.
5. Повторное воздействие: если раздел уже в целевом состоянии, команда не
   отправляется (`already-in-state`, HTTP 409) — «повторное взятие уже
   взятого раздела — нецелевое воздействие» (E11, раздел 8).

Проекция прав (`objects.arm`/`objects.disarm` из `allowedActions`) saving
один раз при входе в запись сессии (`session-store.controlPermissions`).
Старые сессии без поля → «права неизвестны» → управление скрыто (не «нет
прав»: семантика другая). `canArm` — не единственный признак, как и
`allowedActions` — не достаточное подтверждение (требование задачи).

## 6. Проверка фактического состояния и классификация результата

Источники — только подтверждённые E11: `objects/state/` по IMEI (живой
опрос, без кэша) и события журнала `alerts/history-on-obj/`; `obj-details/`
как источник состояния охраны не используется.

Трёхзначность (`observeCommandOutcome`, control-engine):

- **confirmed** — фактическое состояние раздела в карте `objects/state/`
  стало целевым (arm → 2, disarm → 1). `{success: 1}` подтверждением не
  считается — только «команда принята сервером»;
- **rejected** — отказ-код журнала группы 4 **по разделу команды**:
  450.1 «Ошибка снятия» (только при disarm), 450.3 «Ошибка взятия» и
  920.1 «Неисправность при взятии» (только при arm); либо явный HTTP-отказ
  сервера GEORITM (400/500 с `{msg}` — текст передаётся без технических
  деталей); либо `{success: != 1}` («сервер не подтвердил приём»);
- **unknown** — окно наблюдения (75 с, опрос каждые 3 с) истекло без
  перехода и без отказа. Сообщение UI: «Команда принята сервером
  мониторинга, но подтверждение не получено. Проверьте состояние объекта
  перед повтором».

Ошибки опроса состояния и журнала **не превращаются в исход** — наблюдение
продолжается до конца окна (смоук E12.11). Событие с отказ-кодом по другому
разделу, другого действия или запись `ObjectAlertLog` отказом не считаются
(консервативно → unknown, E12.10). Автоматическая повторная отправка
отсутствует: `send` вызывается ровно один раз (смоук E12.8).

### Конфликт с классификатором журнала устранён

Ранее коды 450.1/450.3/920.1 в журнале классифицировались подстрочной
эвристикой группы 4 («Ошибка снятия» содержит «снят») как успешное
**снятие** — отказ выглядел бы подтверждением. Добавлены явные правила в
`VERIFIED_CODES` (georitm-source): `450.1/450.3/920.1 → security_fault`
(в справочнике они `isAlarm=true`, это отказы/неисправности). Новые типы
DTO не вводились до ответа поставщика (E11, 9.2.6); остальные правила
классификатора не изменены.

### Защита от повторных команд

`ControlCommandGuard` (control-engine, память процесса): не более одной
команды на пару «сессия × объект × раздел» (409 `in-flight`); после
`unknown` — cooldown 120 с (повтор заблокирован **сервером**, не только
UI, до успешного опроса состояния); лимит 5 команд/мин на сессию (429).
Рестарт процесса очищает реестр — ослабляет защиту, но не безопасность:
gate, владение и права проверяются при каждом вызове.

## 7. Feature gate

`GEORITM_CONTROL_ENABLED` (lib/account/control-gate.ts):

- отсутствие переменной → **выключено**; включено только `true` (trim,
  регистр не важен); `1`, `yes`, `on`, `TRUE ` и прочее → выключено
  (смоук E12.1);
- проверяется дважды: в диспетчере source.ts (ранний безопасный ответ без
  обращений) и в `executeGeoritmControlCommand` первой строкой — до любого
  вызова GEORITM (смоук E12.14 фиксирует ноль обращений к транспорту);
- браузер повлиять не может: значение читается только из окружения сервера;
- demo-режим подчиняется тому же gate (смоук E12.23);
- скрытого fallback «отправить команду при ошибке проверки» нет: любой
  отказ проверки — `ControlError` с безопасным сообщением.

## 8. UI

Страница объекта, секция «Управление охраной» (client-компонент
`object-control.ui.tsx`, стили в стиле кабинета, адаптивность 375px
проверена):

- при `enabled: false` (выключенный gate) секция не рендерится вовсе;
- при недоступности разделов — пояснение «Управление охраной для этого
  объекта недоступно», без активных кнопок;
- кнопки — только при подтверждённой доступности, по одной на раздел,
  согласно текущему состоянию (снят → «Поставить на охрану», под охраной →
  «Снять с охраны»);
- обязательное подтверждение обоих направлений в модальном диалоге
  («После взятия под охрану движение в охраняемых зонах вызовет тревогу» /
  «Объект останется без охранной защиты этого раздела»);
- во время операции все кнопки секции заблокированы, баннер «Выполняется…»;
- результаты: «Выполнено» / «Отклонено: <текст» / «Результат неизвестен»
  с автоматическим опросом `partitions` каждые 3 с — кнопки остаются
  заблокированными до успешного опроса состояния (повтор — только после
  актуального состояния);
- истина о состоянии — только ответ сервера (`partitions`/ответ команды);
  клиентский кэш и RSC-снимок не источники.

Браузерная проверка (demo, gate включён временно только в локальном
dev-сервере и возвращён обратно): постановка и снятие раздела, диалог,
баннеры, обновление состояния, скрытие раздела с неисправностью, gate off —
секция отсутствует; 375px и тёмная тема — без дефектов вёрстки.

## 10. Ограничения

- Реестр guard/cooldown и demo-оверлей — в памяти процесса: рестарт
  сбрасывает блокировки (безопасность не зависит от них: gate, владение,
  права проверяются всегда).
- Ответ POST-команды удерживается соединением на всё окно наблюдения
  (до ~75 с + опросы); для E12 (gate off) недостижимо, при включении —
  рассмотреть асинхронную схему «принято → опрос partitions», если
  прокси/клиенты не держат долгие запросы.
- `success != 1` классифицирован как `rejected`: документировано только
  значение 1; семантику подтвердить у поставщика (C1).
- Классификация 450.1/450.3/920.1 как `security_fault` в журнале —
  временное решение до подтверждения семантики поставщиком (E11, 9.2.6).
- Подтверждение — переход `objects/state/`; скорость перехода и
  гарантированность доставки отказ-кодов прибором не установлены (E11,
  7.4–7.5).
- `area=0`: разделы с num=0 допускаются командой, если прибор отдаёт их в
  `obj-areas/` и `state/` (валидность `area=0` у GEORITM — открытый
  вопрос E11 7.6).
